# tech-review — 種別判定つき技術文書レビュー

文書種別ごとに読者の目的が違うため、レビュー基準も種別ごとに変わる。このスキルは対象の種別を判定し、
tech-write と共有する原則ファイルのチェックリストで監査する。原則ファイルは
`<このスキルのディレクトリ>/../tech-write/references/` にあり、このスキルは同じ原則を
監査チェックリストとして使う（執筆とレビューで基準がずれないようにするため）。

## 同梱資料の解決

起動時に渡されたスキルの場所 `${CLAUDE_SKILL_DIR}` を、次のコマンドで実体のディレクトリに解決する。
この文字列が未置換のホストでは、スキルを読み込んだときに示されたディレクトリを引数に渡す。
現在の作業場所や個人の固定パスから推測しない。

このコマンドだけを単独の Bash 呼出しで実行し、別のコマンドを連結しない。
終了コードと標準出力を確認してから、資料を読む。
終了コードが 0 で、次に示す順の絶対パス 3 行を得たときだけ、その結果を使う。
失敗、出力なし、行数やパスの不一致では「資料の読取未確認」と失敗した操作を報告し、そこで処理を終了する。
失敗後は別の配備・キャッシュ・作業場所を検索せず、パスを組み立てて読み直さない。
起動時に示された場所以外の資料で代用せず、以下の本文処理・監査・生成・納品へ進まない。
停止の報告を補うための入力読取りや一覧取得も行わず、追加の道具を呼び出さずにその応答を終える。

```bash
python3 -c 'from pathlib import Path; import sys; p = Path(sys.argv[1]).resolve(strict=True); print(p); print(p.parent); print(p.parent.parent / "memorable-doc-principles.md")' "${CLAUDE_SKILL_DIR}"
```

出力の順は、このスキルの実体ディレクトリ、5 スキルを含む `skills` ディレクトリ、規範のパスである。
プラグイン配備では規範に `${CLAUDE_PLUGIN_ROOT}/memorable-doc-principles.md` を使い、上の実体起点の
パスと同じルートの 1 部であることを確認する。開発用 symlink 配備では、プラグイン用変数が未置換でも
実体起点の規範パスを使える。規範のコピーをスキルごとに置かない。

参照を解決したら、規範の全文を Read してから以下の手順へ進む。
存在・サイズの確認、検索で抜き出した一部、要約だけでは全文読取の代わりにならない。
一度で取得できなければ分割して末尾まで読み、未回収が残れば読取未確認を報告して停止する。
適用する観点と強度は各スキルの以下の手順に従い、規範を読んだことだけで適用対象を広げない。

本文の `references/` はこのスキルの実体ディレクトリから、兄弟スキルは解決済みの `skills` ディレクトリ
から読む。`<このスキルのディレクトリ>` も同じ実体を指す。Read の前に絶対パスに直し、references や
別の実行者へ必要な参照を渡すときも解決済みのパスを渡す。references の本文や Bash の中で
プラグイン用変数が自動置換されるとは仮定しない。規範や必要な参照を読めなければ検証失敗とし、
要約だけで読取済みにしない。

生成物・原稿・スキャン結果・スクリーンショットは利用者の作業領域に保存する。
スキルの実体、規範、プラグインキャッシュには書き込まない。指定先がそこに含まれる場合も保存せず、
利用者の作業領域の保存先を確認する。読み取る資料のパスを成果物の保存先に流用しない。

共有規則の適用では、原文・依頼にない事実を本文・図・ラベル・納品報告へ足さない。
検査では各具体的な断定の主体・時点・条件・因果・値を、元の材料と照合する。
材料のない前提・一般化・現在の状態も断定せず、必要な情報は【要確認：必要な情報】で残す。
この照合も既存のセルフチェック・監査へ統合し、HTML の図や報告だけに足した断定も対象にする。
未定の手順を、実装の不存在や利用不能を示す事実として扱わない。
読み手の返答が時計未確認・未計測なら、親の回収時間と区別して未確認として報告する。
起動・回収できたことだけで、全文や時間内の確認済みにしない。修正回数は既存の上限を維持する。

## フロー

1. **読込** — 対象文書を全文 Read する。英日ペア（README.md / README.ja.md 等）を検出したら
   必ず両方読む。Issue/PR コメントの場合はスレッド全体（本文 + 先行コメント）も取得する
   （`gh issue view <n> --comments` / `gh pr view <n> --comments`）—— 返信対象の妥当性は
   スレッドなしに判定できない。対象が HTML のときは、下の「HTML 入力」に従う。
2. **種別判定** — 判定表で種別を決め、判定を表明する：
   「README と判定しました。readme.md の原則で監査します」。
3. **原則ロード** — `<このスキルのディレクトリ>/../tech-write/references/` から該当する原則ファイルと
   `style.md` と `reasoning.md` を Read する。
4. **監査** — 原則ファイル末尾の「レビューチェックリスト」を 1 項目ずつ検査する。style.md の
   検出リストは全文を走査する（日本語文書では S8 の敬体／常体と S9 の記号を含む）。
   同じ場所の `reasoning.md` の規則でも監査し、該当する原文と節を根拠にして指摘する。
   対象が日本語文書なら、目視の走査に先立って機械スキャンを掛け、件数と行番号を得る。英語文書には掛けない：
   `python3 <このスキルのディレクトリ>/../retention-review/scripts/scan.py <対象ファイル> --profile reference`
   Issue・コメントは gh で取得した本文でファイルが無いので、レビュー対象の本文だけを一時ファイルに書き出して掛ける（先行コメントは含めない）。
   出力は S1・S2・S3・S4・S6 と S9（記号の字形。すべて `[弱]`）のシグナルで、判定ではない。`[弱]` と `[引用文脈?]` は該当行を読んで判断する。
   「以下に」「ここでは」は正当な用法にも当たる。手順の「〜してください」とラベルの太字は数えない。記号表記の「**ラベル**。」は、箇条書きのラベルを句点で区切った形（S3）で、ラベルが名詞句なら全角コロンかラベルだけの行への書き直しを指摘する。太字が述語で終わる 1 文なら指摘しない。「**ラベル**:」は、日本語を含む行のラベルを半角コロンで区切った形（S3）で、全角コロンへの書き直しを指摘する。
   指摘一覧の「箇所」には行番号を使い、目視の指摘と並べて報告する。scan.py が使えない環境では、
   style.md の検出リストを目視で確かめる。
   `<このスキルのディレクトリ>/../tech-write/references/reading-pass.md` を Read し、段落の関係を読み、文脈を持たない別の読み手にも対象文書を読ませる。
   指摘は引用・位置・迷う理由とともに既存の監査結果へ統合し、原則列を「段落の関係」にする。
   読み手の指摘も同じ一覧と件数上限へ統合し、実際の解釈を示す。原則列は「文脈を持たない読み手」にする。
   読取の省略・確認範囲・読み手の未実施や時間切れは、同ファイルに従って総評に書く。
5. **報告** — 下のフォーマットで報告する。**対象ファイルは編集しない**。修正の実施を求められたら
   tech-write のプロセスに切り替える。

## HTML 入力

対象が HTML の文書のとき、手順 4 の機械スキャンと目視の走査は本文に掛け、図は別に見る。Markdown とテキストの入力は、このセクションの影響を受けない。scan.py に渡すのは Markdown かテキストだけで、HTML のタグや属性は渡さない。抜き出した本文（または原稿）は、手順 4 でそのまま「対象ファイル」になる。日本語なら `--profile reference` を付けて掛け、英語なら掛けない既存の分岐は変わらない。

| 手元にあるもの | 監査と scan.py に掛けるもの |
|---|---|
| Markdown の原稿がある（その HTML の元の原稿。同じ場所にあるもの・直前に生成したもの・ユーザーが渡したもの） | 原稿。HTML は図の監査にだけ使う |
| HTML だけ | HTML から抜き出した本文。一時ファイルに Markdown として書いてから掛ける |

原稿があるのに HTML から抜き出すのは誤りで、抜き出しは原稿がないときだけにする。

本文の抜き出しは、文書本体（`<body>` の中身。`<body>` タグがなければ `<title>`・`<style>`・`<script>` を除いた全体）の見出しを `#` 見出しに、段落・リスト・表のテキストをそのまま Markdown に写す。`<script>`・`<style>`・`<svg>` の中身、`<figure>` と `<figcaption>`（図とそのラベル）、`aria-label` などの属性、タグは含めない。指摘一覧の「箇所」に書く行番号は、走査した原稿または抜き出した本文の行で、報告の総評にどちらかを書く。本文を抜き出せなかったとき（壊れた HTML・本文が読み取れない構造など）は、抜き出せなかったことを報告に書き、HTML の本文を目視で監査する。

図の監査は、`<このスキルのディレクトリ>/../retention-write/references/html-output.md` の「主役図と補助図」の基準で行い、指摘の原則列を「図」にする。

- 主役図が 1 枚あるか。文書の結論の断定一文を、構造・関係・流れのどれかで絵にした図が、その一文の近くにあるか
- 補助図が、担う役を「この図は〇〇を見せる」と一文で言えるか、主役図と張り合っていないか、消しても読者が困らないなら削ってあるか。1 つでも外れる図は、その図の位置と外れた基準を指摘する
- 図が SVG でなく画像だけのときは、役割と枚数だけを見る。ラベルの検査はしない

スクリーンショットを撮れる環境（html-output.md の「スクリーンショット確認」）では、描画した画面で、はみ出したラベルと交差した線も図の指摘に含める。撮れないときは報告に「スクショ未確認」と書く。本文がほぼなく図だけの HTML は、文書の目的と結論を冒頭の文で述べていない欠落（README なら R1）として指摘する。図は文を補うもので、文書の目的と結論は図の外の文で書かれている必要がある。

## 種別判定表

| 種別 | シグナル | 適用する原則 |
|------|---------|------------|
| README / OSS 入口文書 | `README*.md`、プロジェクト紹介、インストール手順を含む入口文書 | `tech-write/references/readme.md` |
| Issue／チケット | バグ報告、機能要望、タスク起票、GitHub/Jira の Issue | `tech-write/references/issue.md` |
| Issue コメント／PR コメント | 進捗報告、調査結果の共有、レビュー指摘への返信、質問、クローズ理由 | `tech-write/references/comment.md` |
| 主張文書（日本語） | 設計メモ・ADR・提案書・障害報告・意思決定記録 | このスキルではなく **retention-review** に切り替える |
| コード・PR | ソースコード、diff、PR のコード内容自体（コメント文章のレビューは上の行） | このスキルではなく code-review / rite 系に切り替える |
| 未対応種別 | マニュアル、チュートリアル、リリースノート等 | 最も近い原則 + style.md で監査し、報告に「この種別の原則ファイルは未整備」と明示する |

## 報告フォーマット

```markdown
## 総評
(2〜3 文。文書の現状と、直せばどうなるか)

## 指摘一覧
| # | 重要度 | 箇所 | 原則 | 指摘 |
|---|--------|------|------|------|

重要度の基準:
- high — 読者が誤る・迷子になる・使い始められない
- medium — 読みにくさ、乖離リスク(英日不同期・同じ詳細の重複など)
- low — 文体・磨き込み

原則列には該当するものを複数書いてよい(例: R3+R4)。reasoning.md による指摘は同ファイルの節名を書く。HTML の図の指摘は「図」と書く。
各指摘には可能な限り書き直し案を添える(before → after)。書き直し案は報告内のテキスト提案で
あり、対象ファイルには適用しない(「編集しない」原則と矛盾しない)。
書き直し案に、原文にない数値・日付・主体・原因を入れない。値が要る箇所は【要確認: 何が必要か】で
置き、それ以外は完成形の文で示す。

## 問題なしと確認した項目
(チェックして問題がなかった原則を 1 行ずつ列挙する。監査の網羅性を示すため)
```

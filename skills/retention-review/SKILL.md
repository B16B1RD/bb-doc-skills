# 定着レビュー（retention-review）

このレビューが測るのは「読みやすいか」ではない。「読者の頭に 1 週間後も残るか」である。すらすら読める文書ほど、流暢性の錯覚によって何も残さず流れていく——だから読みやすさを褒めるレビューは、ここでは仕事をしていない。

規範：「記憶に残る文書設計の原則」（v0.1）。以下で解決した規範の全文を監査前に Read する（特に 8 原則と付録の対照表）。`references/audit-guide.md` と食い違ったら規範を優先する。

## 同梱資料の解決

起動時に渡されたスキルの場所 `${CLAUDE_SKILL_DIR}` を、次のコマンドで実体のディレクトリに解決する。
この文字列が未置換のホストでは、スキルを読み込んだときに示されたディレクトリを引数に渡す。
現在の作業場所や個人の固定パスから推測しない。

このコマンドだけを単独の Bash 呼出しで実行し、別のコマンドを連結しない。
終了コードと標準出力を確認してから、資料を読む。
終了コードが 0 で、次に示す順の絶対パス 3 行を得たときだけ、その結果を使う。
失敗、出力なし、行数やパスの不一致では「資料の読取未確認」と失敗した操作を報告し、そこで処理を終了する。
失敗後は別の配備・キャッシュ・作業場所を検索せず、パスを組み立てて読み直さない。
起動時に示された場所以外の資料で代用せず、以下の本文処理・監査・生成・納品へ進まない。
停止の報告を補うための入力読取りや一覧取得も行わず、追加の道具を呼び出さずにその応答を終える。

```bash
python3 -c 'from pathlib import Path; import sys; p = Path(sys.argv[1]).resolve(strict=True); print(p); print(p.parent); print(p.parent.parent / "memorable-doc-principles.md")' "${CLAUDE_SKILL_DIR}"
```

出力の順は、このスキルの実体ディレクトリ、5 スキルを含む `skills` ディレクトリ、規範のパスである。
プラグイン配備では規範に `${CLAUDE_PLUGIN_ROOT}/memorable-doc-principles.md` を使い、上の実体起点の
パスと同じルートの 1 部であることを確認する。開発用 symlink 配備では、プラグイン用変数が未置換でも
実体起点の規範パスを使える。規範のコピーをスキルごとに置かない。

参照を解決したら、規範の全文を Read してから以下の手順へ進む。
存在・サイズの確認、検索で抜き出した一部、要約だけでは全文読取の代わりにならない。
一度で取得できなければ分割して末尾まで読み、未回収が残れば読取未確認を報告して停止する。
適用する観点と強度は各スキルの以下の手順に従い、規範を読んだことだけで適用対象を広げない。

本文の `references/` はこのスキルの実体ディレクトリから、兄弟スキルは解決済みの `skills` ディレクトリ
から読む。`<このスキルのディレクトリ>` も同じ実体を指す。Read の前に絶対パスに直し、references や
別の実行者へ必要な参照を渡すときも解決済みのパスを渡す。references の本文や Bash の中で
プラグイン用変数が自動置換されるとは仮定しない。規範や必要な参照を読めなければ検証失敗とし、
要約だけで読取済みにしない。

生成物・原稿・スキャン結果・スクリーンショットは利用者の作業領域に保存する。
スキルの実体、規範、プラグインキャッシュには書き込まない。指定先がそこに含まれる場合も保存せず、
利用者の作業領域の保存先を確認する。読み取る資料のパスを成果物の保存先に流用しない。

共有規則の適用では、原文・依頼にない事実を本文・図・ラベル・納品報告へ足さない。
検査では各具体的な断定の主体・時点・条件・因果・値を、元の材料と照合する。
材料のない前提・一般化・現在の状態も断定せず、必要な情報は【要確認：必要な情報】で残す。
この照合も既存のセルフチェック・監査へ統合し、HTML の図や報告だけに足した断定も対象にする。
未定の手順を、実装の不存在や利用不能を示す事実として扱わない。
読み手の返答が時計未確認・未計測なら、親の回収時間と区別して未確認として報告する。
起動・回収できたことだけで、全文や時間内の確認済みにしない。修正回数は既存の上限を維持する。

## 進め方

### 1. 対象の特定

レビュー対象はファイルパス指定・貼り付けテキスト・直前に生成した文書のいずれか。HTML の文書も対象で、手順 3 と 4 が扱いを足す。曖昧なら確認する。対象が code・API 仕様・英文なら、このスキルの対象外であることを伝えて適切なツール（/code-review 等）を案内する。

### 2. 適用強度の判定

文書タイプで適用する原則を絞る。判定結果は報告の先頭に明記する（間違っていたら依頼者が正せるように）。

| 文書タイプ | 適用原則 |
|---|---|
| 判断を伝える文書（設計メモ・ADR・提案・障害報告・主張のある記事） | 8 原則すべて |
| 短い連絡・議事メモ | 原則 1（賭け金）・3（具体）・6（断定）のみ |
| 参照される文書（API リファレンス・手順書） | 対象外。その旨を伝えて終了 |

連絡メモに物語やクイズを要求するのは過剰適用である。絞る判断もレビューの一部。

### 3. 機械スキャン

対象が HTML のときは、先にこの節の末尾の「HTML 入力の本文」を済ませる。Markdown とテキストの入力は、この手順のまま変わらない。

```bash
python3 <このスキルのディレクトリ>/scripts/scan.py <対象ファイル>
```

太字の数・万能語・ヘッジ表現・文体レジスタ（詠嘆・指示の語形）・前置きフィラー・死んだ比喩・構造宣言・想起テストの有無などを行番号つきで列挙する。貼り付けテキストの場合は一時ファイルに保存してから掛ける。

再レビュー（同じ文書の修正稿を見るとき）は、前回の `--json` 出力を `--baseline` に渡すと差分が resolved（前回あり今回なし）／new（今回のみ）／persisting（両方）に仕分けられる：

```bash
python3 <このスキルのディレクトリ>/scripts/scan.py <修正稿> --baseline <前回の --json 出力>
```

finding の同一性は「カテゴリ + 正規化した該当語」で判定するため、段落の挿入などで行番号がずれただけの違反は persisting のままで new に化けない。修正確認は new（修正が生んだ新しい違反）と resolved（直ったはずの違反）を見る。

スキャン結果はシグナルであって判定ではない。ヒットごとに前後の文脈を読み、著者自身の声かどうかを確認する。引用された悪例・Before/After の「素の文体」側・他者の発言の引用に含まれるヒットは違反ではない。この確認を飛ばすと、良い文書（悪例を引用して説明する文書）を誤って減点する。

#### HTML 入力の本文

scan.py に渡すのは Markdown かテキストだけで、HTML のタグや属性は渡さない。タグごと走査すると、タグの文字列が指摘に出る。

| 手元にあるもの | scan.py に掛けるもの |
|---|---|
| Markdown の原稿がある（その HTML の元の原稿。同じ場所にあるもの・直前に生成したもの・ユーザーが渡したもの） | 原稿。HTML は図の監査（手順 4 の末尾）にだけ使う |
| HTML だけ | HTML から抜き出した本文。一時ファイルに Markdown として書いてから掛ける |

原稿があるのに HTML から抜き出すのは誤りで、抜き出しは原稿がないときだけにする。

本文の抜き出しは、文書本体（`<body>` の中身。`<body>` タグがなければ `<title>`・`<style>`・`<script>` を除いた全体）の見出しを `#` 見出しに、段落・リスト・表のテキストをそのまま Markdown に写す。`<script>`・`<style>`・`<svg>` の中身、`<figure>` と `<figcaption>`（図とそのラベル）、`aria-label` などの属性、タグは含めない。図は手順 4 の末尾で別に見る。

行番号は、scan.py に掛けたファイル（原稿または抜き出した本文）の行を指す。報告の「入力」行にその旨を書き、HTML ソースの行と取り違えられないようにする。再レビューの `--baseline` と、修正の適用の `--preserve` も、抜き出した本文どうし（または原稿どうし）に掛ける。HTML 本体には掛けない。

本文を抜き出せなかったとき（壊れた HTML・本文が読み取れない構造など）は、抜き出せなかったことを報告に書き、HTML の本文を目視で監査する。scan.py の数値は出さない。

### 4. 意味監査

解決済みのスキル実体から `references/scan-guidance.md` の全文を Read する。
弱シグナルは同基準とヒット前後の文脈を照合し、正当な要約・環境依存・事実的不確実性を
空疎な主張と区別する。基準を読めなければ判定未確認として検証失敗を報告し、監査を停止する。

`<このスキルのディレクトリ>/../tech-write/references/reasoning.md` を Read し、共通規則でも監査する。
8 原則との適用と優先順位は同ファイルの「原則との優先順位」に従い、指摘には原文と該当する節を示す。

`references/audit-guide.md` の観点で、適用対象の原則を順に確認する。機械スキャンが拾えない原則——2（因果の物語）・4（スキーマフック）・5（生成の問い）——はここが本体。スキャンに頼れるのは 3・6・7 の一部だけである。

`<このスキルのディレクトリ>/../tech-write/references/reading-pass.md` を Read し、段落の関係を読み、文脈を持たない別の読み手にも対象文書を読ませる。
指摘は引用・位置・迷う理由を付けて［段落の関係］として既存の監査結果へ統合し、手順 5 の最大 7 件に含める。
読み手の指摘も同じ一覧と件数上限へ統合し、実際の解釈を示す。［文脈を持たない読み手］として示す。
読取の省略・確認範囲・読み手の未実施や時間切れは、同ファイルに従って総評に書く。

対象が HTML のときは、本文の監査に加えて図を見る。基準は `<このスキルのディレクトリ>/../retention-write/references/html-output.md` の「主役図と補助図」で、次の 3 点を確かめて［図］の指摘にする。

- 主役図が 1 枚あるか。文書の結論の断定一文を、構造・関係・流れのどれかで絵にした図が、その一文の近くにあるか
- 補助図が、担う役を「この図は〇〇を見せる」と一文で言えるか、主役図と張り合っていないか、消しても読者が困らないなら削ってあるか。1 つでも外れる図は、その図の位置と外れた基準を指摘する
- 図が SVG でなく画像だけのときは、役割と枚数だけを見る。ラベルの検査はしない

スクリーンショットを撮れる環境（html-output.md の「スクリーンショット確認」）では、描画した画面で、はみ出したラベルと交差した線も［図］の指摘に含める。撮れないときは報告に「スクショ未確認」と書く。

本文がほぼなく図だけの HTML は、原則 1（賭け金）の欠落として指摘する。図は文を補うもので、結論の断定一文は図の外の文で書かれている必要がある。

［図］の指摘は、行番号の代わりに図の位置か直前の見出しで示す。書き直しは「削る」か、図が見せるものを一文で決める形でよい。

### 5. 報告

下のフォーマットで報告する。指摘は優先順で最大 7 件。網羅より、直せば最も改善する 1〜3 件に厚みを置く。すべての指摘に、指摘対象の原文引用（行番号つき）と完成形の書き直し案を付ける。書き直し案に、原文にない数値・日付・主体・原因を入れない。値が要る箇所は【要確認: 何が必要か】で置き、残りは完成形の文で示す。

### 6. 修正の適用

求められたときだけ本文を書き直す（「直して」「適用して」等）。報告と同じターンで勝手に書き換えない。レビューの成果物は判断材料であって、修正はユーザーの判断の後にある。HTML 入力のときの適用先は、原稿（なければ抜き出した本文）で、HTML 本体は書き換えない。HTML 化は retention-write と tech-write の HTML 化の手順に任せる。

書き直しを適用する前に、原文を別ファイルへ控える。適用したら、控えと書き直し後を突き合わせる：

```bash
python3 <このスキルのディレクトリ>/scripts/scan.py <書き直し後> --preserve <控えた原文>
```

出力の末尾の「原文からの保持」に、原文にあって書き直し後に残っていない数字とインラインコードが、原文の行番号つきで出る。見るのは数字とバッククォートで囲んだ語だけで、出現回数は比べない。囲まれていない英字の製品名などは拾えないので、書き直した箇所を読んで確かめる。消えた要素は意図した削除かを確認し、意図しないものは戻す。

## 報告フォーマット

```markdown
## 定着レビュー: <文書名>

文書タイプ: 判断文書（8 原則を適用）
機械スキャン: 太字 N 箇所 ／ 万能語 N 件 ／ ヘッジ N 件 ／ 文体レジスタ N 件 ／ 想起テスト 無
（HTML の入力のとき、1 行加える）入力: HTML（走査したのは Markdown 原稿 ／ 抜き出した本文。行番号はその行）

### 既にできている箇所
- <既にできていること 1〜2 件。著者が保持すべきものを先に伝える>

### 指摘（優先順）

1. ［原則 6 断定］ L42「一概にどちらが優れているとは言えません」
   問題: 結論が命題の形をしておらず、読者が想起する取っ手がない。
   書き直し: 「【要確認: 採用案】を採用する。【要確認: 却下案】は【要確認: 却下理由】ため却下。」

2. …

（HTML の入力のとき、図の指摘は区分を［図］にする）
3. ［図］補助図「<図の位置や見出し>」
   問題: 担う役を「この図は〇〇を見せる」と一文で言えない。補助図 3 基準の 1 つ目に外れる。
   書き直し: 削る。残すなら【要確認: 図が見せるべきもの】を一文で決め、図をそれに合わせる。

### 想起テスト 3 問の案（文書に同梱する用）

1. <文書の中身から起案した問い>
2. …
3. …

### 総評

いまの原稿から 1 週間後に読者に残るもの: <正直な予測。「何も残らない」もあり得る>
最優先の一手: <一つだけ>
```

## レビューの心得

- 指摘文も原則に従う。具体で（原文と行を引用）、断定で（「〜かもしれません」と書かない）、書き直し案は完成形で示す。原則に反する文体で原則違反を指摘するレビューは説得力を持たない。
- 書き直し案に事実を作らない。原文にない数値・日付・主体・原因は【要確認: 何が必要か】で置く。【要確認】を含む案にも完成形の要求は変わらず、置き場所以外は完成した文で書く。例：「復旧には【要確認: 所要時間】かかり、顧客影響は返金対応【要確認: 件数】件だった。」作った数字は偽のまま読者に記憶される。
- 想起テストが無い文書には、不在の指摘だけで終えず、文書の内容から 3 問を起案して添える。これはレビューが返せる最も価値の高い成果物で、著者は 3 問に答えようとして初めて自分の文書の空洞に気づく。
- 孤立強調の扱い：強調（太字・色・囲み）2 箇所以上は違反として指摘する。0 箇所は違反ではないが、「読者に残す一文」の候補を 1 つ提案する。
- 文体レジスタの扱い：既定は敬体（です・ます調）だが、常体（である調）で書かれた文書を文体だけを理由に違反にしない。指摘するのは詠嘆・指示の語形（敬体の「〜しましょう。」「〜してください。」、常体の「〜からだ。」「〜してほしい。」）だけで、これは敬体・常体のどちらでも同じ基準である。読者が部下の指示文書と私的な文章はこの基準の例外で、詠嘆・指示レジスタを選んでよい。判断の根拠は `references/audit-guide.md` 原則 6 の文体レジスタの監査。
- 過剰適用も指摘してよい。無理やりな比喩、唐突で答える気にならないクイズ、断定が乱暴になっている箇所——原則のわざとらしい適用を見つけたら、それも指摘する。原則は技巧を足すためではなく、読者の頭に残すためにある。見つけた事例は原則集の「留保」節が求める改訂材料でもあるので、報告の最後に一言添える。
- 数字の指摘は自分も数字で。「太字が多い」ではなく「太字が 12 箇所」。scan.py の出力をそのまま使える。

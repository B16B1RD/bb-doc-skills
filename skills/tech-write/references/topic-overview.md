# 技術トピックの解説の原則

技術トピックの解説は、Git Flow や OAuth のような技術の概念・仕組みを、書き手が調べた事実だけで説明する文書である。
読者は「そのトピックが何で、どういう仕組みかを、元の資料をたどれる形で知りたい」。出典のない説明や、
書き手の好みが混ざった説明では、読者はどこまでが定義でどこからが意見かを区別できず、結局元の資料を探し直すことになる。
そのため、この種別では書き方より先に、事実を一次資料で確かめて出典と確認日を残す手順と、評価を足さない規則を定める。

## 対象の見分け方

依頼の目的が「技術トピックの概念・仕組みを文書で知ること」なら、この種別にする。「Git Flow についてまとめて」
「OAuth の解説を書いて」「このトピックをドキュメントにして」のように、トピックを文書にする依頼が該当する。
文書を求める言い方（「まとめて」「解説を書いて」「ドキュメントにして」）を手がかりにし、「説明して」だけの依頼
（その場で答えればよい質問）はこの種別にしない。

- 採否を決めるための文書（「うちで採用すべきか提案書にまとめて」など、推奨を採るかを決めてもらう文書）は、
  主張文書として retention-write に切り替える。この種別では書かない
- 特定の論文・記事を渡して要点をまとめる依頼は、原典の紹介として `source-summary.md` の原則で書く
- 複数の対象を同じ観点で並べて比べることが主目的の依頼は、調査レポートとして `research-report.md` の原則で書く
- トピックを絵や図解で説明する依頼（「初心者向けに絵で説明して」など）は explain の担当にする
- 手を動かして覚えるチュートリアル・マニュアルは、読者の目的（操作を身につけること）が違うので、未対応種別として扱う

## 原則

### T1. 事実はすべて自分で調べ、事実ごとに出典の URL と確認日を添える

本文の事実は、書き手が自分で調べて確かめたものに限る。手元の知識だけで書かず、各事実に出典のタイトル・URL・確認日を添えて、
読者がたどり直せるようにする。確認日は、その URL を開いて記述を確かめた日である。

- 悪い例：「Git Flow では develop ブランチから feature ブランチを切る」（出典なし）
- 良い例：「feature ブランチは develop から分岐し、develop へ戻す（Vincent Driessen「A successful Git branching model」、https://nvie.com/posts/a-successful-git-branching-model/ 、2026 年 10 月 17 日確認）」
- 検査：本文の事実ごとに、出典の URL と確認日が添えられているか。その URL から同じ記述にたどり着けるか。

### T2. 定義・仕様は一次資料で確かめる

定義・仕様・用語の意味は、一次資料（公式文書・仕様・原著）で確かめる。解説記事・まとめ記事・Q&A サイトは補助にとどめ、
それだけで断定しない。複数の解説記事が一致していても裏付けにはしない。基準は explain スキルの `explain/references/fact-check.md` が
出典として認める一次ソースと同じである。

| 事実の種類 | 認める出典 |
|------------|-----------|
| トピックの定義・提唱者の説明 | 原著（提唱者の記事・論文・書籍） |
| プロトコル・形式の仕様 | 仕様（RFC・各種標準） |
| ツールの機能・コマンド | 公式文書・公式リリースノート |

- 検査：定義・仕様の出典が、公式文書・仕様・原著のどれかか。解説記事だけを出典にした断定がないか。

### T3. 出典を示せない事実は【要確認】で残す

一次資料が見つからない、取得できないなどの理由で出典を示せない事実は、推測や一般知識で埋めない。
本文で書くはずだった箇所を【要確認：確かめられなかった内容】で残し、納品報告にも同じ内容と、試したこと（アクセスした URL と失敗の内容）を書く。

- 検査：出典のない事実が断定で書かれていないか。【要確認】で残した箇所と納品報告の記載が一致するか。

### T4. 扱う事実がいつ時点のものかを本文に書く

技術トピックは、提唱後に改訂されたり、著者が見解を加えたりする。本文に、原典の公開日と、改訂・追記の日付を書き、
事実がいつ時点のものかを読者が分かるようにする。出典ごとの確認日（T1）とは別に、文書全体がどの時点の資料に基づくかも冒頭に書く。

- 良い例：「Git Flow の原典は Vincent Driessen が 2010 年 1 月 5 日に公開した記事で、2020 年 3 月 5 日に著者が振り返りの注記を追加している」
- 検査：原典の公開日と、改訂・追記の日付が本文にあるか。冒頭に、どの時点の資料に基づくかが書かれているか。

### T5. 書き手の評価・採否の推奨を足さない

本文の断定は、出典が述べたことに限る。「優れている」「おすすめ」「使うべき」のような書き手の評価や、採否の推奨を足さない。
出典の中にある評価（提唱者の注記、公式文書の推奨）は、誰の主張かを示して書く（「Driessen は〜と述べている」）。
考え方は `source-summary.md` の O2 と同じである。採否を決めるための文書を求められたら、retention-write に切り替える。

- 悪い例：「Git Flow はリリースが定期的なチームに向いている」（誰の主張か分からない）
- 良い例：「Driessen は 2020 年の注記で、継続的にデリバリーするチームには GitHub Flow のような単純な流れを勧めると述べている」
- 検査：主体のない評価語（「べき」「おすすめ」「優れている」「向いている」など）が本文にないか。出典の評価に主体が付いているか。

### T6. 前提知識がなくても読めるようにする

トピックの用語（ブランチ、マージ、認可サーバーなど）の意味を、最初に出てきた箇所で本文の中で説明する。
用語の説明も事実なので、T1・T2 に従って出典を添える。読者がそのトピックを初めて知る前提で書く。

- 検査：トピックを知らない読者が、冒頭から読んで用語を理解できるか。

## 構成

次の順で節を置く。

1. 冒頭（見出しなし）：トピックが何かを 1〜2 文で述べ、どの時点の資料に基づくかを書く（T4）
2. 概要：トピックの定義と、誰がいつ提唱・策定したか（T2・T4）
3. 仕組み：構成要素と流れ。用語はここで説明する（T6）
4. 改訂と出典の見解：改訂・追記の内容と日付、出典の中にある評価を主体つきで（T4・T5）。なければ節を省く
5. 出典：本文で使った出典の一覧（タイトル・URL・確認日）（T1）
6. 確かめられなかったこと：【要確認】で残した事実と、試したこと（T3）。なければ「なし」と書く

## 執筆プロセス

1. 依頼を確かめる — 採否の推奨や提案を求める部分があれば retention-write への切り替えを伝え、この種別では書かない。
   原典の紹介・調査レポート・explain の依頼に当たらないかも、対象の見分け方で確かめる。
2. 一次資料を探して読む。トピックの原著・仕様・公式文書を特定し、公開日と改訂・追記の日付を控える（T2・T4）。
3. 書く事実を抜き出し、事実ごとに出典の URL と確認日を控える（T1）。一次資料で確かめられない事実は、試したことと一緒に控える（T3）。
4. 構成の順に書く。用語は本文で説明し（T6）、出典の評価は主体を付けて書く（T5）。
5. 照合する — 本文の各事実と控えた出典を突き合わせ、出典を示せない断定を除くか【要確認】に直す。主体のない評価語を除く。
6. 納品報告に、使った一次資料、どの時点の資料に基づくか、【要確認】で残した事実と試したことを書く。

## レビューチェックリスト（tech-review 用）

監査では、解説が添えた出典の URL をたどれる範囲でたどり直す。たどれないときは、その事実を「出典未確認」として報告し、
事実の正否を判定しない。

- [ ] T1：本文の事実ごとに、出典の URL と確認日が添えられ、たどり直せるか
- [ ] T2：定義・仕様の出典が一次資料（公式文書・仕様・原著）か。解説記事だけで断定していないか
- [ ] T3：出典を示せない事実が【要確認】で残り、納品報告も渡されていれば同じ内容が載っているか
- [ ] T4：原典の公開日と改訂・追記の日付、どの時点の資料に基づくかが本文にあるか
- [ ] T5：書き手の評価・採否の推奨がなく、出典の評価が誰の主張かを示して書かれているか
- [ ] T6：用語の意味が本文で説明されているか

- [ ] style.md S9：日本語の稿の記号が規定どおりか

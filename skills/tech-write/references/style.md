# 共通文体規範 — AI 文体・冗長性の検出と矯正

生成 AI の文章には特有の癖があり、読者は数行で「水増しされた文章だ」と感知して読み飛ばしモードに入る。
参照文書での読み飛ばしはそのまま情報の見落としになる。執筆・レビューの双方で、以下を機械的に走査する。

## 検出リスト

### S1. 前置きフィラー

文書や節の冒頭で、内容を予告するだけの文。見出しがすでにその役割を果たしている。

- 日本語：「本ドキュメントでは〜について説明します」「以下に〜を示します」「ここでは〜を紹介します」
- 英語："This document describes...", "In this section, we will...", "Let's take a look at..."
- 矯正：削除して本題から始める
- 機械検出：`scan.py --profile reference` の「前置きフィラー」

### S2. 万能語（具体性ゼロの形容）

どの製品・機能にも貼れる形容詞は情報量がゼロで、かえって信頼を下げる。

- 日本語：強力な・柔軟な・シームレスな・包括的な・効率的に・簡単に・迅速に・洗練された
- 英語：powerful, flexible, seamless, comprehensive, robust, effortlessly, easily, blazingly fast
- 矯正：削除するか、検証可能な事実に置換する
  - 例：「柔軟な設定」→「YAML で 12 項目を上書き可能」
- 機械検出：`scan.py --profile reference` の「万能語」

### S3. 太字の乱発

1 段落に複数の太字があると、強調は機能しなくなる。

- 例外：箇条書き先頭のラベル的 bold（`- **名前**：説明`）は文書の慣習として許容する。
  検出対象はそれに加えて文中に現れる inline bold
- 日本語の文書のラベル：この項目が決めるのは区切りの字形だけで、ラベルを太字にするかどうかは上の規定に従う。ラベルと説明は全角コロンで区切る（`- **実行時の発見**：ワーカーは……`）。説明が長いときは、ラベルだけの行の下に字下げして説明を書く。句点で区切らない（`- **実行時の発見**。ワーカーは……`）。名詞句のラベルが 1 文として立ち、日本語として読めない。直すのはラベルが名詞句のときだけで、太字が述語で終わる 1 文（`- **事実リストより先に HTML を書かない**。……`）なら句点のままでよい
- 矯正：ラベルを除き、太字は 1 節に 1〜2 か所まで。「全部大事」は「何も大事でない」と同じ
- 機械検出：`scan.py --profile reference` の「太字（ラベルを除く）」

### S4. 両論併記・過剰ヘッジ

参照文書は断定が仕事。条件を明示しないぼかしは読者に判断を丸投げしている。

- 日本語：「場合によっては」「〜かもしれません」「一般的には」の条件抜きの使用
- 英語："in some cases", "may or may not", "it depends"（条件の明示なし）
- 矯正：条件を特定して断定する（「X の場合は A、それ以外は B」）。本当に不明なら「未検証」と書く
- 機械検出：`scan.py --profile reference` の「ヘッジ・両論併記」

### S5. 同義反復・水増し

同じ情報の言い換え連打、内容が重複する箇条書き項目。

- 矯正：読者の知識が増えない文は削除する。

誰も言っていないことを打ち消してから本題を言う形も、ここに含める。

- 日本語：「これは単なる設定ではなく、運用の決まりです」「このツールは魔法ではなく、ただのスクリプトです」
- 対象外：実際に検討して退けた案の記録（原則 6 の却下案）は、誰かが挙げた案なので、ここに含めない
- 矯正：読者が打ち消した側に取り違えそうなとき（前の節や広く知られた見方がそう読ませるとき）だけ残す。それ以外は打ち消しを外し、本題だけを書く。何を打ち消すかを命題として正確にする規則は `reasoning.md` の「否定と譲歩を正確にする」に従う

### S6. 空虚な結び

- 日本語：「ぜひご活用ください」「お役に立てれば幸いです」
- 英語："We hope you find this useful!", "Happy coding!"
- 矯正：削除。参照文書に挨拶は不要
- 機械検出：`scan.py --profile reference` の「空虚な結び」

### S7. 語は文書の分野に合わせて選ぶ

語は、その文書が扱う分野の読者が普段読み書きしている語を使う。辞書に載っている語でも、別の分野の語を持ってこない。新しい漢語の名前も作らない。
日本語の文書に適用する。英語文書と英日ペアの英語側には適用しない（S8・S9 と同じ扱い）。

同じ語でも、分野で正否が変わる。

| 語 | 正しい分野 | ソフトウェアの文書で、この意味に使うと誤り | そのときに書く語 |
|---|---|---|---|
| 正本 | 法律・契約の文書（判決の正本、契約書の正本） | source of truth | 「〜を基準にする」「〜が元のデータ」のような素直な文 |
| 版 | 書籍・文書の改訂（第 2 版） | ソフトウェアの version | バージョン |
| 鍵 | 暗号（公開鍵、秘密鍵） | 設定・辞書の key | キー |
| 署名 | 電子署名 | 関数の signature | シグネチャ |
| 道具 | 工具・日用品（大工の道具） | tool（CLI・ライブラリ・サービス） | ツール |
| 枝 | 植物（木の枝） | Git やパッケージの branch | ブランチ |
| 試験 | 資格・学校の試験。負荷試験・試験運用のような定着した複合語 | ソフトウェアの test | テスト |

表は例で、全部ではない。表に無い語も同じ検査に掛ける。表の語は、機械スキャン（`retention-review/scripts/scan.py`）が「語の分野」の `[弱]` のシグナルとして、単独の名詞の形で拾う。本来の分野の用法にも当たるので、行を読んで判断する。表に無い語と、表の語でも前が空白の形（`CI 試験`）・複合語（`版番号`）などは拾わないので、目視で拾う。

- ソフトウェアの分野で定着しているカタカナ語・英字の語を、漢語や和語に置き換えない。定着した語が読者に通じないときは、語を替えずに初出で 1 回だけ説明を添える。対象の製品の公式ドキュメントの日本語が漢語で書いている語（default value を「既定値」と書くなど）は、この行より下の行に従って、そちらに合わせる
- 「平易に」「やさしく」と頼まれても、定着した語を別の分野の語や自作の漢語に替えない。平易にするのは文の組み立てと説明で、語の置き換えではない
- 英語の概念を書くときは、元の英語を思い浮かべ、その分野の日本語の文書（対象の製品の公式ドキュメントの日本語、対象のリポジトリの既存の文書）がその概念をどう書いているかに合わせる
- 定着した訳が無ければ、英語のまま書いて初出で 1 回だけ説明するか、素直な文で言う。訳語を自作しない
- 既存の文書への追記・部分改訂では、その文書がすでに使っている用語を継ぐ。この行は表の「そのときに書く語」より優先する。継いだ語が分野に合わないときは、書いた範囲の中では継いだまま、合わない語と箇所を納品報告に 1 行で書く
- 作業中に読んだ手引き・指示の文の言葉づかいを、書く文書へ持ち込まない。手引きが別の分野の語で書かれていても、書く文書は文書の分野の語で書く
- レビューの書き直し案・修正案の文も、この規則で書く

検査：

- 文書の中の漢語・和語の名詞と動詞のうち、ソフトウェアの概念（ツール・手続き・データ・役割）を指しているものを 1 つずつ拾う
- 拾った語を英語の概念に戻し、その概念を日本語の技術文書が普通どう書くかと比べる。違えば、普通の書き方に直す
- その語が本来の分野の意味で使われているなら（契約書の正本、公開鍵、書籍の第 2 版）、指摘しない。漢語であることだけを理由に直さない（default を「既定値」と書く製品の文書もある）
- 初出より後で説明が付き添う名前は失敗
- 1 語に 2 つの意味を持たせない

既存の文書を書き直すときは、反対向きの失敗もある。原文の漢語を和語に開きすぎない。

- 例：原文の「確認する」「停止する」を、読みにくいという理由なしに「確かめる」「止める」へ書き換える。「結果の確かめ」「処理の止め」のような、動詞の連用形を名詞にした語を作る
- 矯正：書き直す箇所でも、語の選び方は原文のまま保つ。読み手が止まる語だけを替え、替えた語には、何が読みやすくなったかを言えるようにする。言えない置き換えは戻す

### S8. 敬体と常体

日本語の参照系技術文書の既定は「です・ます」（敬体）である。英語文書には適用しない。敬体と常体は日本語固有の区別である。

上書きは次の 2 つだけで、優先は上が強い。

1. 指示文に「である調で」「常体で」「だ・である調で」があれば「である調」で書く。「です・ます調で」「敬体で」があれば「です・ます」で書く
2. 既存文書への追記・部分改訂ではその文書の文体を継ぐ。である調の README に節を足すなら「である調」で書き、同一文書内で混ぜない

どちらにも当てはまらなければ「です・ます」で書く。文書の種別（README／Issue／手順書）からは既定を推定しない。

手順書・コマンド説明の命令形は違反ではない。参照系技術文書では手順の命令が内容そのものである。

- 正当：「依存関係をインストールしてください。」「`make build` を実行します。」
- 違反：「一緒に始めましょう。」（読者への呼びかけであり、手順の命令形ではない）
- 矯正：呼びかけは削除するか、手順の命令・事実の記述に置換する。英語文書は触らない

タイトルと見出し（Markdown の `#` 行、Issue / PR のタイトル）は敬体／常体の対象外である。

検査：

- 日本語の新規文書が、上書きなしで「である調」になっていないか
- 英語文書に敬体／常体を適用していないか
- 手順の「〜してください」を違反として消していないか
- 英日ペアでは日本語側にだけ適用しているか（構造一致は R6）
- 読者への呼びかけ（「〜しましょう」「〜ですよね」）が残っていないか
- 同一文書の本文内で敬体と常体が混在していないか

### S9. 記号

日本語の文書では括弧・コロン・区切りなどの記号を次の表の字形にそろえ、用途を絞って使う。英語文書と英日ペアの英語側には適用しない（S8 と同じ扱い）。対象は記号だけで、数字と英字は全角にしない（「32 件」の書き方は変えない）。

| 記号 | 名称 | 用途 |
|------|------|------|
| ・ | 中点 | 並列する語句の区切り |
| ／ | スラッシュ | 並列する語句の区切り。「または」の意味にも使う |
| ： | コロン | 「例：」のように例を示すとき、用語や記号を説明するとき、箇条書きのラベルと説明を区切るとき（S3） |
| 〜 | 波形（U+301C） | 範囲を示す |
| …… | 三点リーダー | 省略を示す（2 個一組を標準にする） |
| （） | 丸括弧 | 直前の内容の説明・補足 |
| 「」 | かぎ括弧 | 名称・用語・選択肢などの固有名詞。発言・文章の引用にも使う |
| 『』 | 二重かぎ括弧 | 書籍・雑誌などの作品名。かぎ括弧の中のかぎ括弧 |
| ［］ | 角括弧 | ボタンやリンクの名称（太字で表してもよい） |
| “ ” | 引用符（U+201C・U+201D） | 用語を取り上げて言及するとき。文の強調には使わない |

範囲の記号は U+301C の「〜」にする。U+FF5E の「～」は正規化（NFKC）で半角の `~` に変わるため取り込まない。文の強調は従来どおり太字 1 か所を優先する。

疑問符と感嘆符は全角（？！）で書き、本文では多用しない。ハイフン（-）とセミコロン（；）は和文の記号として使わない（JTF 3.2.1・3.2.2・3.2.6・3.2.8。JTF は S12 の基準のスタイルガイド）。住所や電話番号の区切りのハイフンは別である（JTF 3.2.6）。英語の語句とコードの中の記号も別である。

半角のまま残す場所：

- コードスパン・コードフェンス・URL・コマンド
- Markdown の構文（`**`、表の `|`、見出しの `#`、リストの `-`）
- ファイル名とパス、`A/B` のような英語の表記
- HTML のタグ・属性・CSS・スクリプト（HTML の本文にある日本語には適用する）
- 日本語の文字を含まない行（`- **Type**: fix` のように、ラベルも値も英字だけの行）。判定は行ごとで、ラベルが英字だけでも説明が日本語の行は、S3・S9 の対象のままにする

既存文書への追記・部分改訂では追記・改訂した行だけ表に従う。触っていない既存行は直さない。

- 例：「（」を半角の `(` で書く、範囲を半角の `~` で書く
- 矯正：表の字形に直す。引用の「」を “ ” に書き換えない

検査：

- 括弧・コロン・並列の記号が表の字形でそろっているか
- 範囲が U+301C の「〜」になっているか
- “ ” を文の強調に使っていないか
- 疑問符と感嘆符が全角か。和文にハイフンとセミコロンを使っていないか
- コード・URL・パス・Markdown 構文の半角を直していないか
- 数字と英字を全角にしていないか
- 英語文書に適用していないか

### S10. 段落の論点と長さ

1 つの段落では 1 つの独立した論点を扱う。結論・理由・例がその論点を支えるなら同じ段落に置ける。文の数と論点の数を同一視しない。

日本語では通常は 2〜4 文程度・100〜200 字程度を執筆の出発点にする。5 文以上または 250 字以上なら、分ける必要があるかを確認する弱い目安になる。違反の境界や読みやすさの保証ではない。1 文で足りる結論を水増しせず、短くても独立した論点が複数なら分ける。1 つの因果や条件を説明する長い段落は、まとまりを確認して残せる。

- 技術文書：別の論点は別段落かラベル付き項目、同じ属性を繰り返す比較・移動・変更は表にする。各節の先頭に結論を 1 文置く。
- 判断を伝える文章：因果の物語を保つ。出来事・原因・結果の意味の切れ目で段落を分け、前後の因果を示す文を残す。段落を短くするために表や箇条書きへ変えない。
- 情報保持：主体・条件・数値・例外を配置先へ対応付ける。目安に収めるために情報を削らない。長いセルや項目への移動だけでは解消にならず、セル・項目も 1 つの論点かを目視で確かめる。

#### 計数の定義と範囲

長さを機械計測する対象は通常の日本語の地の文の段落だけとする。ソフト改行・ハード改行は同じ段落として扱う。リスト配下全体（継続・入れ子を含む）／引用配下全体／表・セル／見出し／フェンス・字下げコード／frontmatter／HTML ブロックは計測から除く。除外は目視の点検を免除する意味ではない。

字数は空白を除いた Unicode コードポイント数。リンクは表示文字、強調は本文を数え、リンク先・インラインコード・画像・HTML タグは数えない。文数相当は「。！？!?」の連続を区切りとし、文末記号のない残りも 1 文相当とする。地の文中の短いかぎ括弧の引用も含め、小数・URL のピリオドでは分けない。言語学的な文認定ではなく近似で、英語文が混在すると過小計数になる場合がある。

日本語の数値目安を英語へ機械適用しない。英日ペアは意味と構造を同期する既存の規則に従う。対象外や抽出不能を該当 0 件で代用せず、未計測の範囲を示す。段落の論点は長さを計測できなくても目視で点検する。

- 検査：段落の独立論点、結論から理由・条件へのつながり、移した情報の保持を確かめる。長さの目安を超えたことだけでは違反としない。
- 矯正：論点の境目を選んで分け、因果・条件と必要な具体を残す。機械指摘 0 件を完成の条件にしない。
- 計測：`scan.py` は両 profile で通常の日本語段落の長さを弱く表示する。開始・終了行／文数相当・字数／対象数・最大値を確認し、採否と分ける。JSON の `paragraph_length` は計測済みなら配列、未計測なら `null` と `paragraph_measurement` の理由で示し、統計も `null` とする。対応する構文と非対応の扱いはスクリプトの docstring に従い、完全な Markdown 構文対応を前提にしない。
- 比較：段落長の baseline は対象数・該当件数・最大値を比べ、移動の同一性を追わない。旧形式・未計測は比較不能で、解消と扱わない。HTML は元 Markdown を優先し、抽出本文の構造が失われたら `--paragraphs-unmeasured` に理由を指定して段落長だけを未計測とする。

### S11. 読点

読点は文の大きな切れ目にだけ打つ。読点は文の構造の切れ目を読者に知らせる記号である。多すぎると大きな切れ目と小さな切れ目の区別がつかなくなり、1 つもない長い文では読者が係り先を読み誤る。英語文書と英日ペアの英語側には適用しない（S8・S9 と同じ扱い）。見出し・コード・表・引用は対象外で、引用した文の読点は直さない。

読点を打つ場所：

- 長い修飾語句が 2 つ以上並ぶときの境目
- 長い条件や理由の節の後（「設定を変えたあと再起動しないまま保存した場合、」）
- 語順を入れ替えて短い語句を前に出したときの、その語句の後
- 読点がないと別の語に係って読める位置。「今日発表した資料を送る。」と「今日、発表した資料を送る。」では資料を送る日が違う
- 修飾語の付いた語句を並べるときの語句の間

読点を打たない場所：

- 短い主題の「は」の後（「この関数は空の配列を返す。」）。「では」「には」「としては」のように助詞に「は」が付いた短い語句と、「書くのは」「どれを使うかは」のように節に「は」が付いた短い主題も同じに扱う。主題が長いときと、主題の直後に長い修飾語句が続くときは打つ
- 「A を B に」のような短い成分の間
- 同じ文に、より大きな切れ目の読点があるときの小さな切れ目。大きな切れ目の読点だけを残す

1 文に読点が 3 つ以上あるときは、小さな切れ目の読点を消すか文を分ける。消す順番は、短い主題の後・短い成分の間・文頭の短い副詞（「実際」「以降」など）の後とする。長い条件や理由の節の後と、係り先を分ける読点は残す。修飾語の付かない名詞の並び（「A、B、C」）は S9 の中点でつなぐ。修飾語の付いた語句の並びで読点が 3 つ以上になるなら、文を分けるか箇条書きにする。40 字を超える文に読点が 1 つもないときは、係り先が 1 つに決まるかを確かめる。

- 例：「この関数は、入力が空のとき、空の配列を、返す。」では 4 つの切れ目が同じ重さに見える。「入力が空のとき、この関数は空の配列を返す。」と書く
- 矯正：上の順に読点を消すか文を分ける。語を変えずに直せるなら語を変えない。どの読点を残すかは前後の文で決まるので、同じ字面でも一括で消さない

検査：

- 1 文に読点が 3 つ以上ないか
- 文頭の短い主題（「〜は」「〜では」「〜には」）の後に読点を打っていないか
- 40 字を超えて読点のない文で、係り先が 1 つに決まるか
- 引用した文や英語文書に適用していないか

機械検出：`scan.py` の「読点の多い文」（両 profile の弱シグナル）が、括弧とコードの外に読点が 3 つ以上ある文を拾う。1 行ずつ見て、行の中を文末の記号で文に分ける（文の途中で折り返した文は、行ごとに数える。URL の直後の半角の「!」「?」は URL の一部とみなす）。コードスパン・コードフェンス・表・ATX の見出し・引用行と、例示のラベル（「例：」など）で始まる行は数えない。URL と HTML のタグ（< … > の中）の読点も数えない。字下げのコードと Setext の見出しは数える。短い主題の後の読点と、40 字を超えて読点のない文は検出しないので目視で確かめる。

### S12. 日本語の表記

日本語の文書の表記は『JTF日本語標準スタイルガイド（翻訳用）第4.0版』（表紙の日付は 2026 年 7 月 25 日。以下 JTF）に沿う。JTF が扱うのは表記の統一だけで、文の組み立て（S1〜S7・S10）とは重ならない。敬体と常体（S8）・記号（S9）・読点（S11）の規則は各節に書き、ここには写さない。英語の文書と英日ペアの英語側には適用しない（S8・S9・S11 と同じ扱い）。JTF の節番号を添えた文が JTF の決めである。節番号の無い所と「この節は」「この節の決め」と書いた所は、このスキル群の決めである。

- 見出し：体言止めか常体にし、句点を付けない（一般向けのマニュアルでは「〜には」「〜とは」で止めてもよい）。見出しの間で形をできるだけ混ぜない（JTF 1.1.2）
- 箇条書き：ひとまとまりの中で敬体と常体を混ぜず、文末の句点の有無をそろえる。本文が常体なら敬体を使わない（JTF 1.1.3）
- 句点：かぎ括弧・丸括弧を閉じる直前に打たない（JTF 3.1.1）。文末の形を見せるために引いた文（S8 の「一緒に始めましょう。」）は残してよい（この節の決め）
- 文字の幅：漢字・ひらがな・カタカナは全角で書き、半角カタカナは特殊な用途を除いて使わない（JTF 2.1.1・2.1.2・2.1.5）。数字と英字を半角で書くことは S9 に従う
- 漢字：常用漢字表に原則として準じる。表に無い漢字でも、実務で慣用的に用いられる語（推敲・罫線・梱包など）は漢字で書く（JTF 2.1.2）
- ひらがな：形式名詞・補助動詞・接続詞と一部の副詞はひらがなで書く（こと・とき・ため・ください・できる・および・または・ただし・したがって・さらに・なお・あらかじめ。JTF 2.2.1）。どちらも一般的な語（すでに／既に、すべて／全て、わかる／分かる）は文書の中でそろえ、迷ったらひらがなにする（JTF 2.2.1）
- 送りがな：動詞は本則と例外に従い、許容の形を使わない（行う・表す・取り消す。JTF 2.1.3）。複合語の動詞も、原則として省かない（書き込む・取り扱う。JTF 2.1.4）。派生した名詞は、JTF は省いた形も認めてそろえることを求めていて、この節は省かない形にそろえる（取り扱い・呼び出し・引き継ぎ）。省いた形が定着した名詞は省く（取締役・申込書。JTF 2.1.4）
- カタカナ複合語：区切らずに書き、読み誤りそうなときだけ中黒で区切る。JTF 2.1.7 は中黒・半角スペース・区切りなしのどれかにそろえることを求めていて、この節は区切りなしを選ぶ
- 数字：数えられるもの（任意の数に置き換えても通じる語句）と序数は算用数字、慣用句・熟語・概数・固有名詞は漢数字で書く（1 つ・第 2 回／一部・第三者・数百倍。JTF 2.2.2）。助数詞は「か」にする（3 か月。JTF 2.2.3 は「か」か「カ」で、この節は「か」を選ぶ）。桁区切りにはカンマ（省いてもよい）、小数点にはピリオドを使い、半角にする（JTF 2.1.10・3.1.3）

カタカナ語の末尾の長音は、原則として省略しない（JTF 2.1.6）。-er・-or・-ar で終わる語は、長音を付けて書く。後ろに語が続く形も同じに書く（サーバーレス・ユーザー名。この節の決め）。ユーザビリティ・サーバントは別の語で、ここには当たらない。

| 語の終わり | 長音を付けて書く語 |
|---|---|
| -er | ユーザー・サーバー・ブラウザー・フォルダー・コンピューター・パラメーター・ヘッダー・フッター・プリンター・ドライバー・メンバー・レジスター・カウンター・コンテナー |
| -or | エディター・セレクター |
| -ar | カレンダー |

表は例で、全部ではない。-y で終わる語も、JTF の原則は長音を付ける形（メモリー）である。そのうえで JTF 2.1.6 は、業界や分野によって運用にゆれがあるとし、同じ文書の中で統一することを求めている。この節は、そのゆれの範囲で、ソフトウェアの分野で長音なしが定着した語（メモリ・ディレクトリ・リポジトリ・ライブラリ・カテゴリ・セキュリティ・プロパティ）を長音なしで書くことを選ぶ。ほかの -y の語は、どちらの形でもよく、語ごとに文書の中でそろえる。製品の公式ドキュメントが別の形で書く語は、S7 のとおりそちらに合わせる。

JTF の決めと逆にするのは、全角と半角の間のスペースだけである。JTF 2.3.1.1 は入れない形で、この節は入れる形を選ぶ。

- 半角の英数字かコードスパンと、漢字・ひらがな・カタカナの間には、半角スペースを 1 つ入れる（「README を書く」「32 件」「`scan.py` の出力」）
- 全角の記号（句読点・括弧・中点など）との間と、全角文字どうしの間には入れない。括弧の内側と外側も同じ（「API（`gh api`）」「S8・S9」。JTF 2.3.1.2・2.3.3）
- 英語の語句の中のスペースは残す（Visual Studio Code。JTF 2.3.1.3）。英字や記号の単位（MB・px・% など）と数値の間には入れない（10MB・50%。JTF 2.3.2 は、実務翻訳では一般的に入れないとしていて、この節は入れない形を選ぶ）。漢字・ひらがな・カタカナの単位（秒・分・件・円・ピクセルなど）は、1 つ目の項のとおり数値との間に入れる（10 秒・3 件）。英字や記号の単位の後ろに日本語が続くときも、1 つ目の項と同じに入れる（10MB の・50% を）
- リンクと太字は表示される文字で決める。リンクの文字が日本語なら前後に入れない（`[導入案内](x.md)を使う`）

Markdown では次の 2 つで表示が崩れる（この節の決め）。

- URL の直後に日本語の字を続けると、GitHub はその字までリンク先に含める。URL の後に半角スペースを置くか、`< >` で囲むか、リンクにする
- 太字の中身の端に括弧・句読点・コードスパンを置くと、前後が文字のとき太字にならないことがある（`これは**「重要」**です。`）。記号を太字の外へ出す（`「**重要**」`）か、太字の外側に半角スペースを置く。このスペースは太字を成り立たせるためのもので、上のスペースの規則（全角の記号・全角文字との間に入れない。太字は表示される文字で決める）の例外である

優先は上が強い（S7・S8 と同じ向き）。

1. 利用者の指示（「全角と半角の間にスペースを入れないで」「長音は付けないで」など）
2. 対象の文書がすでに持つ書き方。追記と部分的な書き直しでは、その文書の書き方を継ぐ（スペースを入れない書き方でそろった文書には入れない）。ただし、全角文字どうしの間のスペースは、どちらの書き方の文書でも入れないので、追記・書き直した範囲の中では入れない。用語は製品の公式ドキュメントの書き方（S7）
3. 投稿先の制約（`channels/` のファイル。Slack の書式の記号の前後のスペースなど）
4. どれにも当てはまらなければ、この節

どの場合も、コード・コマンド・URL・パス・画面の文言・製品名・作品名・引用した文は書き換えない。

- 例：`サーバを起動する` と書く。`READMEを書く` と `README を書く` を同じ文書に混ぜる
- 矯正：この節の形に直す。書き換えないものと、優先の順で上の書き方を持つ文書は直さない

レビューでの扱い（レビューのスキルはここに従う）：

- 表記の指摘は種類ごとに 1 件にまとめ、件数と例の行番号を添える。重要度は内容の指摘より下（low）に置く
- 書き方（スペースのあり・なし、長音のあり・なし、数えるものを算用数字で書くか漢数字で書くか、など）ごとに、文書の状態から、指摘と注記を次の表で決める

| 文書の状態 | 指摘 | 注記 |
|---|---|---|
| 全体がこの節の形でそろっている | 出さない | 書かない |
| 混ざっていて、多いほうがこの節の形 | 少ないほうを多いほうにそろえる指摘を出す | 書かない |
| 混ざっていて、多いほうがこの節と違う形（`サーバ` が多い） | 少ないほうを多いほうにそろえる指摘を出す（多いほうがこの節と違っても、この節の形にそろえる指摘にはしない） | 1 件書く（多いほうがこの節と違うこと）。多いほうが JTF のとおりの書き方（スペースなし、`メモリー`）なら書かない |
| 混ざっていて、同じ数 | この節の形にそろえる指摘を出す（この節がどちらの形でもよいとする -y の語は、どちらかの形にそろえる指摘） | 書かない |
| 全体がこの節と違う形でそろっている（-er・-or・-ar の語がどれも長音なし、など） | 出さない（箇所ごとに挙げない） | 1 件書く。JTF のとおりの書き方（スペースなし、`メモリー`）なら書かない |

- 多いほうにそろえるのは、多いほうが、その文書がすでに持つ書き方（優先の順の 2）だからである
- この節と違っても JTF のとおりの書き方（スペースを入れない書き方と、メモリーのように -y の語に長音を付ける書き方）には、どの行でも注記を書かない。そろえる指摘は、表のとおり出す（スペースなしが多い混ざった文書は、指摘を出して注記は書かない。全体がスペースなしの文書は、指摘も注記も無い）
- 長音は、同じ語で分かれる形（`サーバ` と `サーバー`）のほかに、-er・-or・-ar の語が語によって分かれる形（`サーバー` と `ブラウザ`）も、混ざっていると数える。-y の語は語ごとに見る
- 機械スキャンの「長音の抜け」が出すのは長音なしの所だけなので、長音ありの所（`サーバー`）は本文で数える
- これはレビューする文書の扱いで、新しく書く文書は、この節の形（メモリ）で書く

検査：

- 見出しと箇条書きの文体・句点がそろっているか。括弧を閉じる直前に句点を打っていないか
- ひらがな・送りがな・数字が上の形か。-er・-or・-ar の語の長音が抜けていないか
- -y の語と、英数字と日本語の間のスペースが、文書の中でそろっているか。全角文字どうしの間にスペースが入っていないか。URL の直後に日本語の字が続いていないか
- 書き換えないものと英語の文書を直していないか

機械検出：`scan.py` の 5 つの弱シグナル（両 profile）が次を拾う。コードスパン・コードフェンスと『』（作品名）の中は見ない（字下げのコードブロックは見る）。リンクの宛先として除くのは `[文字](宛先)` の形だけで、参照定義の宛先は見る。英数字と日本語の間と全角文字どうしの間は、`>` で始まる引用行を見ない。ほかの項目は拾わないので、目で見る。

- 「長音の抜け」：表の語を長音なしで書いた所
- 「URL の直後の日本語」：`http://`・`https://` で始まる URL にスペースなしで漢字・かなが続く所（`www.` で始まる形は拾わない）。`/` で終わる URL に漢字・カタカナが続く形（`https://example.com/日本語`）は、日本語のパスと見分けられないので拾わない（ひらがなが続く形は拾う）
- 「英数字と日本語の間」：境目のスペースのあり・なしの数と、なしの行（なしが多い文書では、ありの行も出す）。`%` のような記号と日本語の境目（`50%を`）は数えない
- 「全角文字どうしの間」：漢字・ひらがな・カタカナと、全角の句読点・中点・コロン・セミコロン・括弧のうち、2 字の間の半角スペース 1 つ。全角の！？の後（JTF 3.2.1・3.2.2）は拾わない。太字の印（`**`・`__`）の外側のスペースは、太字を成り立たせるためかを見分けずに全部拾わないので、`これは **重要** です` のような所は目で見る。人の名前の姓と名の間のような正当なスペースにも当たる
- 「数えるときの漢数字」：漢数字 1 字（一〜九）の後に「つ」が続く所（`二つ`・`三つ目`）。数を置き換えられない慣用句のうち、決めた一覧（`一つひとつ`・`何一つ`・`二つ返事`・`瓜二つ` など）は拾わない。ほかの助数詞（`三回`・`二人`・`十二個`）は拾わないので、目で見る。一覧に無い慣用句（`身一つ`）には当たるので、行を読んで残す

# 共通文体規範 — AI 文体・冗長性の検出と矯正

生成 AI の文章には特有の癖があり、読者は数行で「水増しされた文章だ」と感知して読み飛ばしモードに入る。
参照文書での読み飛ばしは、そのまま情報の見落としになる。執筆・レビューの双方で、以下を機械的に走査する。

## 検出リスト

### S1. 前置きフィラー

文書や節の冒頭で、内容を予告するだけの文。見出しが既にその役割を果たしている。

- 日本語：「本ドキュメントでは〜について説明します」「以下に〜を示します」「ここでは〜を紹介します」
- 英語："This document describes...", "In this section, we will...", "Let's take a look at..."
- 矯正：削除して本題から始める。
- 機械検出：`scan.py --profile reference` の「前置きフィラー」

### S2. 万能語（具体性ゼロの形容）

どの製品・機能にも貼れる形容詞は情報量がゼロで、かえって信頼を下げる。

- 日本語：強力な、柔軟な、シームレスな、包括的な、効率的に、簡単に、迅速に、洗練された
- 英語：powerful, flexible, seamless, comprehensive, robust, effortlessly, easily, blazingly fast
- 矯正：削除するか、検証可能な事実に置換する。
  - 例：「柔軟な設定」→「YAML で 12 項目を上書き可能」
- 機械検出：`scan.py --profile reference` の「万能語」

### S3. 太字の乱発

1 段落に複数の太字があると、強調は機能しなくなる。

- 例外：箇条書き先頭のラベル的 bold（`- **名前**：説明`）は文書の慣習として許容する。
  検出対象は、それに加えて文中に現れる inline bold。
- 日本語の文書のラベル：この項目が決めるのは区切りの字形だけで、ラベルを太字にするかどうかは上の規定に従う。ラベルと説明は全角コロンで区切る（`- **実行時の発見**：ワーカーは……`）。説明が長いときは、ラベルだけの行の下に字下げして説明を書く。句点で区切らない（`- **実行時の発見**。ワーカーは……`）。名詞句のラベルが 1 文として立ち、日本語として読めない。直すのはラベルが名詞句のときだけで、太字が述語で終わる 1 文（`- **事実リストより先に HTML を書かない**。……`）なら句点のままでよい
- 矯正：ラベルを除き、太字は 1 節に 1〜2 箇所まで。「全部大事」は「何も大事でない」と同じ。
- 機械検出：`scan.py --profile reference` の「太字（ラベルを除く）」

### S4. 両論併記・過剰ヘッジ

参照文書は断定が仕事。条件を明示しないぼかしは読者に判断を丸投げしている。

- 日本語：「場合によっては」「〜かもしれません」「一般的には」の条件抜きの使用
- 英語："in some cases", "may or may not", "it depends"（条件の明示なし）
- 矯正：条件を特定して断定する（「X の場合は A、それ以外は B」）。本当に不明なら「未検証」と書く。
- 機械検出：`scan.py --profile reference` の「ヘッジ・両論併記」

### S5. 同義反復・水増し

同じ情報の言い換え連打、内容が重複する箇条書き項目。

- 矯正：読者の知識が増えない文は削除する。

### S6. 空虚な結び

- 日本語：「ぜひご活用ください」「お役に立てれば幸いです」
- 英語："We hope you find this useful!", "Happy coding!"
- 矯正：削除。参照文書に挨拶は不要。
- 機械検出：`scan.py --profile reference` の「空虚な結び」

### S7. 名前を作る前に

新しい漢語の名前を当てる前に、既存の一般語か素直な文で言えないかを試す。言えるならそちらを使う。英語概念に訳語を自作しない。

- 例：「正本」を source of truth の訳に使う
- 矯正：一般語か素直な文に戻す。新しい名前を作らない。

検査：

- 初出より後で説明が付き添う名前は失敗
- 1 語に 2 つの意味を持たせない
- 英語概念に当てた漢語の辞書的意味がずれていないか

### S8. 敬体と常体

日本語の参照系技術文書の既定は です・ます（敬体）である。英語文書には適用しない。敬体と常体は日本語固有の区別である。

上書きは次の 2 つだけで、優先は上が強い。

1. 指示文に「である調で」「常体で」「だ・である調で」があれば である調で書く。「です・ます調で」「敬体で」があれば です・ますで書く
2. 既存文書への追記・部分改訂では、その文書の文体を継ぐ。である調の README に節を足すなら である調で書き、同一文書内で混ぜない

どちらにも当てはまらなければ です・ますで書く。文書の種別（README／Issue／手順書）からは既定を推定しない。

手順書・コマンド説明の命令形は違反ではない。参照系技術文書では手順の命令が内容そのものである。

- 正当：「依存関係をインストールしてください。」「`make build` を実行します。」
- 違反：「一緒に始めましょう。」（読者への呼びかけであり、手順の命令形ではない）
- 矯正：呼びかけは削除するか、手順の命令・事実の記述に置換する。英語文書は触らない。

タイトルと見出し（Markdown の `#` 行、Issue / PR のタイトル）は敬体／常体の対象外である。

検査：

- 日本語の新規文書が、上書きなしで である調になっていないか
- 英語文書に敬体／常体を適用していないか
- 手順の「〜してください」を違反として消していないか
- 英日ペアでは日本語側にだけ適用しているか（構造一致は R6）
- 読者への呼びかけ（「〜しましょう」「〜ですよね」）が残っていないか
- 同一文書の本文内で敬体と常体が混在していないか

### S9. 記号

日本語の文書では、括弧・コロン・区切りなどの記号を次の表の字形にそろえ、用途を絞って使う。英語文書と英日ペアの英語側には適用しない（S8 と同じ扱い）。対象は記号だけで、数字と英字は全角にしない（「32 件」の書き方は変えない）。

| 記号 | 名称 | 用途 |
|------|------|------|
| ・ | 中点 | 並列する語句の区切り |
| ／ | スラッシュ | 並列する語句の区切り。「または」の意味にも使う |
| ： | コロン | 「例：」のように例を示すとき、用語や記号を説明するとき、箇条書きのラベルと説明を区切るとき（S3） |
| 〜 | 波形（U+301C） | 範囲を示す |
| …… | 三点リーダー | 省略を示す（2 個一組を標準にする） |
| （） | 丸括弧 | 直前の内容の説明・補足 |
| 「」 | かぎ括弧 | 名称・用語・選択肢などの固有名詞。発言・文章の引用にも使う |
| 『』 | 二重かぎ括弧 | 書籍・雑誌などの作品名。かぎ括弧の中のかぎ括弧 |
| ［］ | 角括弧 | ボタンやリンクの名称（太字で表してもよい） |
| “ ” | 引用符（U+201C・U+201D） | 用語を取り上げて言及するとき。文の強調には使わない |

範囲の記号は U+301C の「〜」にする。U+FF5E の「～」は、正規化（NFKC）で半角の `~` に変わるため取り込まない。文の強調は従来どおり太字 1 箇所を優先する。

半角のまま残す場所：

- コードスパン・コードフェンス・URL・コマンド
- Markdown の構文（`**`、表の `|`、見出しの `#`、リストの `-`）
- ファイル名とパス、`A/B` のような英語の表記
- HTML のタグ・属性・CSS・スクリプト（HTML の本文にある日本語には適用する）
- 日本語の文字を含まない行（`- **Type**: fix` のように、ラベルも値も英字だけの行）。判定は行ごとで、ラベルが英字だけでも説明が日本語の行は、S3・S9 の対象のままにする

既存文書への追記・部分改訂では、追記・改訂した行だけ表に従う。触っていない既存行は直さない。

- 例：「（」を半角の `(` で書く、範囲を半角の `~` で書く
- 矯正：表の字形に直す。引用の「」を “ ” に書き換えない。

検査：

- 括弧・コロン・並列の記号が表の字形でそろっているか
- 範囲が U+301C の「〜」になっているか
- “ ” を文の強調に使っていないか
- コード・URL・パス・Markdown 構文の半角を直していないか
- 数字と英字を全角にしていないか
- 英語文書に適用していないか

### S10. 段落の論点と長さ

一つの段落では、一つの独立した論点を扱う。結論・理由・例がその論点を支えるなら同じ段落に置ける。文の数と論点の数を同一視しない。

日本語では、通常は 2〜4 文程度・100〜200 字程度を執筆の出発点にする。5 文以上または 250 字以上なら、分ける必要があるかを確認する弱い目安になる。違反の境界や読みやすさの保証ではない。1 文で足りる結論を水増しせず、短くても独立した論点が複数なら分ける。一つの因果や条件を説明する長い段落は、まとまりを確認して残せる。

- 技術文書：別の論点は別段落かラベル付き項目、同じ属性を繰り返す比較・移動・変更は表にする。各節の先頭に結論を 1 文置く。
- 判断を伝える文章：因果の物語を保つ。出来事・原因・結果の意味の切れ目で段落を分け、前後の因果を示す文を残す。段落を短くするために表や箇条書きへ変えない。
- 情報保持：主体・条件・数値・例外を配置先へ対応付ける。目安に収めるために情報を削らない。長いセルや項目への移動だけでは解消にならず、セル・項目も一つの論点かを目視で確かめる。

#### 計数の定義と範囲

長さを機械計測する対象は、通常の日本語の地の文の段落だけとする。ソフト改行・ハード改行は同じ段落として扱う。リスト配下全体（継続・入れ子を含む）、引用配下全体、表・セル、見出し、フェンス・字下げコード、frontmatter、HTML ブロックは計測から除く。除外は目視の点検を免除する意味ではない。

字数は空白を除いた Unicode コードポイント数。リンクは表示文字、強調は本文を数え、リンク先・インラインコード・画像・HTML タグは数えない。文数相当は「。！？!?」の連続を区切りとし、文末記号のない残りも 1 文相当とする。地の文中の短いかぎ括弧の引用も含め、小数・URL のピリオドでは分けない。言語学的な文認定ではなく近似で、英語文が混在すると過小計数になる場合がある。

日本語の数値目安を英語へ機械適用しない。英日ペアは、意味と構造を同期する既存の規則に従う。対象外や抽出不能を該当 0 件で代用せず、未計測の範囲を示す。段落の論点は、長さを計測できなくても目視で点検する。

- 検査：段落の独立論点、結論から理由・条件へのつながり、移した情報の保持を確かめる。長さの目安を超えたことだけでは違反としない。
- 矯正：論点の境目を選んで分け、因果・条件と必要な具体を残す。機械指摘 0 件を完成の条件にしない。
- 計測：`scan.py` は両 profile で通常の日本語段落の長さを弱く表示する。開始・終了行、文数相当・字数、対象数・最大値を確認し、採否と分ける。JSON の `paragraph_length` は計測済みなら配列、未計測なら `null` と `paragraph_measurement` の理由で示し、統計も `null` とする。対応する構文と非対応の扱いはスクリプトの docstring に従い、完全な Markdown 構文対応を前提にしない。
- 比較：段落長の baseline は対象数・該当件数・最大値を比べ、移動の同一性を追わない。旧形式・未計測は比較不能で、解消と扱わない。HTML は元 Markdown を優先し、抽出本文の構造が失われたら `--paragraphs-unmeasured` に理由を指定して段落長だけを未計測とする。

## 適用方法

- 執筆時：納品前に全文を上から走査し、該当箇所を矯正してから出す。
- レビュー時：「検出箇所／分類（S1〜S10）／書き直し案」の形で報告する。

# Issue／チケットの原則

Issue の読者は 2 人いる — 「今、着手判断をする実装者」と「数ヶ月後に検索で辿り着く調査者」。
どちらも Issue を開いて 1 分で「これは何で、自分に関係があるか」を判断したい。

## 原則

### I1. タイトルは検索可能な変更要約

動詞 + 対象で、一覧表示や検索結果の中で内容が判別できること。「バグ修正」「〜について」は不可。

- 良い例：「CSV 取り込みが馬名の全角スペースで KeyError になる」
- 検査：タイトルだけを読んで、何のどんな問題／変更か言えるか。

### I2. 種類に応じた必須要素

- バグ：再現手順（番号付き）／期待動作／実際の動作／環境。期待と実際は必ず分離する。
- 機能・タスク：目的（なぜやるか）／完了条件（何をもって完了とするか、検証可能な形で）。
- 検査：バグなのに再現手順がない、機能なのに完了条件がない状態を弾く。

### I3. 自己完結

読者が別の場所を探さずに済むこと。関連ファイルはパスで、エラーメッセージは原文をコードブロックで、
関連 Issue/PR はリンクで示す。「例のあの問題」「先日話した件」は数ヶ月後の読者には無意味。

- 検査：この Issue 単体で、着手判断に必要な情報が揃っているか。

### I4. スコープ境界

やらないことを明記する。境界のない Issue は実装中に膨張する。

- 検査：「やらないこと」「Out of scope」相当の記述があるか（自明に小さい Issue は免除）。

### I5. 1 つの Issue に 1 関心事

「ついでに」が入った Issue は分割する。レビューも履歴追跡も 1 関心事単位でしか機能しない。

### I6. 未確定事項の明示

決めきれていない点は Open Questions として列挙する。書かなければ実装者の暗黙の推測で埋まり、
それは高確率で起票者の意図とずれる。

起票者の未決事項だけでなく、報告された主張自体への疑義も対象にする。報告の因果が技術的に
不整合に見える・再現が未確認、といった場合は、勝手に補正したりそのまま転記したりせず、
「未確認です。着手時に◯◯を確認します」と明示して記録する。

## プロジェクト固有テンプレートとの関係

対象リポジトリに Issue テンプレート（`.github/ISSUE_TEMPLATE/`、rite workflow の
Implementation Contract 等）がある場合、構造はテンプレートに従う。この原則は構造の代替ではなく
品質基準として適用する（テンプレートを埋めていても I1〜I6 を満たさない Issue はある）。

## 執筆プロセス

1. 種類（バグ／機能／タスク）を判定する。
2. リポジトリのテンプレート有無を確認する。確認できない場合は、I2 の必須要素をそのまま
   骨組みとして使う。
3. I2 の必須要素を先に埋める（本文の体裁より先に）。
4. I3〜I6 を満たす形で本文化する。
5. style.md で走査する（Issue では前置きフィラーと過剰ヘッジが出やすい）。日本語の敬体／常体は
   S8 に、記号は S9 に従う。

## レビューチェックリスト（tech-review 用）

- [ ] I1: タイトル単体で内容が判別できるか
- [ ] I2: 種類に応じた必須要素が揃っているか
- [ ] I3: 単体で着手判断できるか（パス・エラー原文・リンク）
- [ ] I4: スコープ境界があるか
- [ ] I5: 複数の関心事が混ざっていないか
- [ ] I6: 未確定事項が明示されているか
- [ ] style.md S8: 日本語 Issue の敬体／常体が規定どおりか
- [ ] style.md S9: 日本語 Issue の記号が規定どおりか

# マニュアルの原則

マニュアルの読者は「製品を使って、自分の作業を終わらせたい」人。頭から通して読まない。作業の途中で開き、要る箇所だけを読んで、製品に戻る。
この読者に対する文書の仕事は 3 つ —（1）やりたい作業から、その手順にたどり着かせる（2）書かれたとおりに操作すれば、書かれたとおりの結果になる
（3）画面の項目・オプション・設定・エラーを、名前で引けるようにする。

## 対象の見分け方

ソフトウェアの製品（アプリ・Web サービス・コマンドのツール）を使う人のために、複数の作業の手順と調べるための一覧をまとめた文書を、この種別にする。
操作マニュアル・ユーザーガイド・管理者ガイド・運用マニュアル・ソフトウェアの取扱説明書が当たる。コマンドやオプションの一覧・設定項目の一覧・
よくある質問・トラブルシューティングのように、マニュアルの一部だけを頼まれたときも、この種別にする。

- 1 つの作業だけを書かれたとおりに進める文書（インストール手順・セットアップ手順・チュートリアル・運用の手順書）は、手順書・チュートリアルとして `procedure.md` の原則で書く
- 機器（ハードウェア）の取扱説明書は、この種別にせず、未対応種別として扱う。機器の安全の警告は、リスクアセスメントの結果を材料に要するため
- 社内の業務の進め方をまとめた業務マニュアルは、製品の使い方でなく仕事の進め方と判断の基準を伝える文書で、参照系技術文書に当たらない。tech-write・tech-review の対象にしない
- リポジトリの入口の文書は README の原則（`readme.md`）で書く
- 複数のページからなるドキュメントサイトは、ページごとに種別を判定する。マニュアルと判定したページは、そのページの中の章を M2 で立てる。どのページを置くか・ページをどの順に並べるか・サイトのナビゲーションをどう作るかは、この原則では決めない
- 製品に限らない技術トピックの概念・仕組みの解説は `topic-overview.md` で書く

## 原則

### M1. 対象の製品・バージョン・読者・確かめた日を冒頭に書く

製品の名前とバージョン・想定する読者（役割と既に知っていること）・マニュアルの内容を現物と合わせた日を、最初の節より前に書く。
バージョンが現物から読み取れなければ【要確認】で残す。

- 検査：冒頭だけを読んで、自分の使っているバージョンのマニュアルか、自分が読者に当たるかが分かるか。

### M2. 章は読者の作業で立てる。画面や機能の順に並べない

読者が製品でやりたい作業を並べ、それを章・節の見出しにする。見出しは作業を表す文にする。
画面の部品やメニューの並び（「ヘッダー」「サイドパネル」「設定画面」）を章にしない。項目の一覧は参照の節（M5）に置く。
機能を全部載せることを目標にしない。読者がする作業に要るものを載せ、載せなかった作業や機能は納品報告に並べる。

- 悪い例：「1. 画面の構成」「2. 起動オプション」「3. コメントモード」
- 良い例：「文書を開く」「直してほしい箇所に朱を付ける」「付けた朱を渡して直してもらう」
- 検査：目次だけを読んで、やりたい作業の節を選べるか。作業の節の見出しが、画面の部品や機能の名前だけになっていないか

### M3. 概念・手順・参照・つまずいたときを、別の節に分ける

1 つの節には、次の 4 つの種類のうち 1 つだけを書く。

- 概念：何か・なぜそうなっているか
- 手順：どう操作するか
- 参照：項目の一覧
- つまずいたとき：症状・原因・直し方

手順の途中に、仕組みや理由の説明を入れない。
1 つの手順の期待結果と違ったときの案内は、手順の一部として、その手順の直後に書く（`procedure.md` の H4）。
つまずいたときの節には、特定の手順に結び付かない症状と、エラーメッセージの文言から引く読者のための一覧を置く。
手順に要る前提だけを手順の前に置き、背景は概念の節に書いて、手順からはその節を指す。

- 検査：番号付きの手順の中に、操作でも期待結果でもない説明の文が無いか。参照の表の中に手順が入っていないか。

### M4. 手順は 1 手順に 1 操作。場所を先に、操作を後に書く

手順の節は `procedure.md` の H3（1 つの操作とその期待結果）・H4（期待結果と違ったときの案内）・H6（後始末）に従う。
画面の操作では、どの画面のどの部分かを先に書き、次に操作を書く。手順の前には、その作業で何ができるかを 1 文と、始める前に要るものを書く。

- 悪い例：「直してほしい箇所をクリックして、入力欄に内容を書いて保存します」
- 良い例：「1. 本文の、直してほしい箇所をクリックする。右の欄に入力欄が出る。」「2. 入力欄に、どう直してほしいかを書く。」
- 検査：1 つの手順に操作が 2 つ以上入っていないか。各手順に期待結果があるか。操作の場所が操作より前に書かれているか

### M5. 参照の節は製品での並びか名前の順に、同じ形で並べる

画面の項目・コマンドのオプション・設定・終了コード・エラーメッセージの一覧は、製品での並び順か名前順に並べ、
項目ごとに同じ欄（名前・意味・取れる値・既定値）で書く。読者が指定する項目と画面や出力で目にする項目は、現物にあるものを全部載せる。
一部だけを載せるときは、載せた範囲を節の頭に書く。製品の内部のデータ（検出する語の辞書、内部の定数など）は全部を写さず、何がどこにあるかを示す。
全部を写すと文書が伸び、読者が要る項目を見つけにくくなる。

- 検査：読者が指定する項目と目にする項目を、現物と 1 つずつ突き合わせる。抜けた項目と、現物に無い項目が無いか。項目ごとに欄がそろっているか。内部のデータを全部写した一覧が無いか。

### M6. 画面の文言・オプションの名前・既定値は現物と一字一句合わせ、確かめた方法を控える

現物とは、製品のコード・実行した画面や出力・利用者が渡した仕様書や画面の画像をいう。ボタンやメニューの名前は、画面に出る文字のまま書き、言い換えない。日本語の稿は `style.md` の S9 のとおり［］で囲む。S9 は太字も許すが、マニュアルでは太字にしない。マニュアルには画面の名前が多く出るので、太字にすると S3 の上限（ラベルを除き 1 節に 1〜2 か所）を超えるため。
事実ごとに確かめた方法（ファイルと行、実行したコマンドと出力、渡された資料の箇所）を控える。
現物を読めない・動かせないときは、渡された材料にあることだけを書く。材料に無い画面の文言や既定値は推測で埋めず、【要確認】で残す。

- 悪い例：画面のボタンが「朱を付ける: 入」なのに、本文で「コメントモード: ON」と書く。
- 検査：本文に出る画面の文言・オプションの名前・既定値・上限・保存先を拾い、現物と 1 つずつ突き合わせる。
  突き合わせた範囲と、突き合わせられなかった範囲を報告する。

### M7. 同じものを 1 つの名前で呼ぶ。名前は製品の画面の語にそろえる

製品の画面や出力が使う語を、そのまま使う。同じものを 2 つ以上の名前で呼ばない。読者が知らない語は、最初に出た所で説明するか、用語の一覧に載せる。

- 検査：同じものを指す語が 2 つ以上無いか（朱・コメント・注釈・指摘のように）。

### M8. 注意と警告は、当たる手順の前に置く。材料に無い警告を作らない

データが消える操作や元に戻せない操作の注意は、その手順より前に書く。現物や材料にある注意は落とさない。
現物や材料から確かめられない危険を、一般知識で足さない。

- 検査：注意が、当たる手順の後ろに置かれていないか。現物にある注意（確認のメッセージ、エラーの文）が落ちていないか。

### M9. 画面の画像を、文の代わりにしない

操作に要る情報は文で書き、画像にしか無い情報を作らない。画像は、利用者が渡したものか、書き手が実際の画面を撮ったものだけを使う。作り物の画面を描かない。
画像が無いときは、画像なしで読める文にする。画像を足すと読者が助かる箇所は、納品報告に、位置と撮る画面を並べる。

- 検査：画像を読めない読者が、文だけで操作できるか。画像と本文の文言が食い違っていないか。

### M10. 文体

`style.md` の検出リストを全文に適用する。手順の命令形は違反ではない（S8）。日本語文書の敬体／常体は `style.md` の S8 に、
記号は S9 に、表記は S12 に従う。

## 執筆プロセス

1. 対象の製品・バージョン・読者を決める。現物（コード・実行できる製品・渡された資料）がどこにあるかを確かめる。
2. 読者の作業を並べる — 現物と既存の文書から、読者が製品でする作業を拾う。どの作業を載せるかが決まらなければ、作業が分岐する不明点として聞く。
   質問できないときは自分で決め、載せなかった作業を納品報告に書く（M2）。
3. 目次を作る — 作業ごとの手順の節・概念の節・参照の節・つまずいたときの節に分ける（M3）。
4. 現物を読み、動かせるものは動かして、確かめた方法を控えながら書く（M4・M6）。動かすのは作業用の一時フォルダーで、利用者のリポジトリは変えない。
5. 参照の一覧を現物と 1 つずつ突き合わせる（M5）。本文の用語をそろえる（M7）。
6. style.md で全文を走査する。

納品報告には、現物と照合した範囲・照合できなかった範囲・載せなかった作業や機能・画像を足すと助かる箇所を書く。

## 言語

英語と日本語の両方に対応する。英語の依頼には英語で、このファイルの原則（M1〜M10）をそのまま使う。
style.md の S8・S9・S11・S12 と機械スキャン（`scan.py`）は、日本語の稿にだけ掛ける。

## レビューチェックリスト（tech-review 用）

監査では、製品の現物（コード・渡された資料）を読んで照合する。製品も文書のコマンドも実行しない。
現物がどこにあるかが依頼からも文書からも分からないときは、M5・M6 を「現物と照合できなかった」と報告し、問題なしにしない。
現物から読み取った事実は、確かめた方法（ファイルと行）を添えて書き直し案に入れてよい。

- [ ] M1：冒頭で、対象の製品・バージョン・読者・確かめた日が分かるか
- [ ] M2：目次だけを読んで、やりたい作業の節を選べるか。章が画面の部品や機能の順になっていないか
- [ ] M3：手順の中に概念の説明が、参照の表の中に手順が混ざっていないか
- [ ] M4：1 つの手順に操作が 1 つで、期待結果があり、場所が操作より前にあるか
- [ ] M5：参照の一覧に、現物にある項目の抜けと、現物に無い項目が無いか
- [ ] M6：画面の文言・オプションの名前・既定値が、現物と一字一句合っているか
- [ ] M7：同じものを 2 つ以上の名前で呼んでいないか
- [ ] M8：注意が当たる手順の前にあるか。現物にある注意が落ちていないか
- [ ] M9：画像にしか無い情報が無いか
- [ ] M10：style.md の検出リスト（S8・S9・S11・S12 を含む）に引っかかる箇所はないか

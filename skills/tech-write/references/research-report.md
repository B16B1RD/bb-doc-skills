# 調査レポートの原則

調査レポートは、書き手が自分で調べた結果を伝える文書である。読者は「何をどこまで調べ、何が確かめられ、
何が確かめられなかったかを知って、自分の判断に使いたい」。確かめていないことが確かめたことと同じ調子で
書かれていると、読者はどこを信じてよいか分からず、結局すべてを調べ直すことになる。そのため、この種別では
書き方より先に、調べる範囲の決め方と、事実ごとに確かめた方法を残す手順を定める。

## 対象の見分け方

依頼の目的が「調べた結果を知ること」なら、この種別にする。対象は次の 2 系統である。

| 系統 | 中身 | 例 |
|------|------|-----|
| 比較調査 | 複数の対象を同じ観点で比べ、最後に推奨を置く | 技術選定の比較、競合のベンチマーク |
| 検証・計測のレポート | 対象と再現方法、計測した結果、限界を書く | 検出器の誤検出率の計測、設定値の校正 |

- 推奨そのものが主目的の文書（提案書）は、主張文書として retention-write に切り替える。見分け方は、tech-write の
  判定表にある「ハイブリッド文書は主目的（読者がその文書を開く理由）で決める」に従う。読者が調べた結果を知るために開くなら調査レポート、
  推奨を採るかどうかを決めるために開くなら提案書とする
- 調べた題材を絵や図解で説明する依頼（「この 3 つの違いを初心者向けに絵で説明して」など）は explain の担当にする
- 課題の調査メモ（現状・該当箇所・修正方針・影響を書くもの）は Issue として `issue.md` の原則で書く
- スクリプトが自動生成するレポートは対象にしない
- スレッドに付ける調査結果のコメントは Issue コメント／PR コメントの種別で書き、事実と確かめた方法の書き方だけこのファイルの V2・V3 に従う

## 調べる作業

tech-write は、調べる作業も自分で行う。Web 検索、ファイルやコードを読むこと、コマンドを実行して測ること、
必要なら使い捨ての測定スクリプトを書いて実行することまで含む。調べる作業をほかのスキルや利用者に任せる前提で書かない。

- 測定スクリプトや計測の出力は、作業用の一時フォルダ（`mktemp -d` で作ったフォルダなど）に置いて動かす。利用者のリポジトリにはファイルを作らず、既存のファイルも変えない
- 計測の前後で `git status --short` を取り、利用者のリポジトリが変わっていないことを確かめる。変わっていたら元に戻し、納品報告に書く
- 実行したコマンドと出力は、再現方法として本文に載せる。測定スクリプトを書いたときは、その全文も載せる（一時フォルダは納品後に消えるため）
- 作業量の上限は設けない。決めた範囲の中は全部確かめる

## 原則

### V1. 調べる範囲を先に決めて冒頭に書く

書き始める前に、調べる範囲（対象と比べる観点、計測なら対象・条件・指標）を決める。利用者が対象や観点を指定しなければ
tech-write が選び、選んだ理由を書く。決めた範囲は本文の冒頭に、調査の問いと一緒に書く。範囲を後から広げたり狭めたりしたら、冒頭も直す。

- 良い例：「対象は A・B・C の 3 ライブラリ（GitHub のスター数が上位の 3 つを選んだ）。観点はライセンス、最終リリース日、依存の数」
- 検査：冒頭だけ読んで、何をどの観点で調べたか、対象を選んだ理由が分かるか。

### V2. 断定は確かめたことだけにし、事実ごとに確かめた方法を添える

本文の各事実に、確かめた方法を添えて、読み手がたどり直せるようにする。方法は事実の種類に合わせて次のどれかを書く。

| 確かめた方法 | 添えるもの |
|--------------|-----------|
| 出典を読んだ | 出典のタイトルと URL（確認した日付を添える） |
| ファイルやコードを読んだ | ファイルのパスと行（GitHub のコードなら commit SHA 付きの permalink） |
| コマンドを実行した | 実行したコマンドと出力の原文（コードブロック） |

ブランチ参照の行リンクは、後の変更で行がずれて死ぬので使わない。確かめた方法を示せない文は、断定せず V4 に回す。

- 悪い例：「B は A より速い」
- 良い例：「B の処理時間は 1.2 秒、A は 3.4 秒だった（下の『再現方法』のコマンドを 5 回実行した中央値）」
- 検査：本文の事実ごとに、確かめた方法が添えられているか。添えられた URL・行・コマンドから同じ事実にたどり着けるか。

### V3. 事実と解釈を分ける

観測した事実（読んだ記述、実行したコマンド、ログ、出力の原文）と、そこから導いた解釈・仮説を分けて書く。
解釈には「〜と考える」「〜の可能性がある」のように解釈であることが分かる書き方をし、根拠にした事実を示す。

- 検査：読者が事実だけを見て、書き手と別の解釈を立てられる状態か。

### V4. 確かめられなかったことは、名前を挙げて残す

手を尽くしても確かめられなかった対象や観点（出典を取得できない、測る手段がない、など）は、推測で埋めない。
次の 3 か所に残す（`source-summary.md` の O1 で、一部しか読めなかった原典を扱う規則と同じ考え方）。

- 本文の「調べられなかったこと」の節：対象や観点の名前と、何をどこまで試したか（実行したコマンドやアクセスした URL と失敗の内容）
- 納品報告：同じ対象や観点の名前
- 本文でそれについて書くはずだった箇所：【要確認：確かめられなかった内容】で残す（比較表のセルも同じ）

確かめられなかったことがなければ、「調べられなかったこと」の節に「なし」と書く。

- 検査：「調べられなかったこと」の節と納品報告の両方に、同じ名前が挙がっているか。書くはずだった箇所が【要確認】で残っているか。

### V5. 再現方法を載せる

検証・計測のレポートでは、対象（版やコミット）、環境、実行したコマンドと出力を「再現方法」の節に載せ、
読者が同じ手順で同じ結果を得られるようにする。比較調査でも、計測した観点があれば同じように載せる。
出力が長いときは、結果に使った部分を省略せずに載せ、省いた箇所は省いたと書く。

- 検査：「再現方法」の節のコマンドを順に実行すれば、本文の数値を得られるか。対象の版と環境が書かれているか。

### V6. 結果には限界を添える

計測した条件（データの件数・種類、環境、回数）と、試していない条件を、結果と同じ節に書く。結果だけを並べると、
読者は調べていない範囲まで成り立つと読む。

- 検査：各結果の近くに、計測した条件と試していない条件が書かれているか。

### V7. 推奨は結果と分けて末尾の節に置く

推奨を書くときは、結果の節と分けて文書の末尾の「推奨」の節に置く。各推奨に、どの調査結果に基づくかを、結果の節や表の行を指して示す。
推奨を読まなくても、結果の節だけで読者が使える形にする。結果の節に推奨や評価の言葉（「おすすめ」「優れている」）を混ぜない。

- 良い例：「B を使う。ライセンスが社内規定に合うのは B だけだった（結果の表のライセンスの行）」
- 検査：推奨の節が末尾にあり、各推奨に根拠の結果への参照があるか。推奨の節を消しても、結果の節が読めるか。

### V8. 前提知識がなくても読めるようにする

調査の問い、それがなぜ問題なのか、専門用語の意味を本文の中で説明する。読者が依頼の経緯を知らない前提で書く。

- 検査：依頼の経緯を知らない読者が、冒頭から読んで問いと用語を理解できるか。

## 構成

次の順で節を置く。比較調査で推奨を求められていなければ、「推奨」の節は省く。

1. 冒頭（見出しなし）：調査の問いと、それがなぜ問題か（V8）
2. 調べた範囲：対象・観点・選んだ理由（V1）
3. 結果：観点ごとの事実と確かめた方法（V2・V3・V6）。比較調査では対象×観点の表を置く
4. 再現方法：対象の版・環境・コマンドと出力（V5）
5. 調べられなかったこと：対象や観点の名前と、試したこと（V4）
6. 推奨：各推奨と根拠の結果（V7）

## 執筆プロセス

1. 依頼を確かめる — 推奨そのものが主目的なら retention-write への切り替えを伝え、この種別では書かない。
2. 書き始める前に調べる範囲を決める（V1）。対象や観点の指定がなければ選び、選んだ理由を控える。
3. 調べる。事実ごとに、確かめた方法（URL と確認日、ファイルと行、コマンドと出力）を控える。計測は一時フォルダで行い、
   前後で利用者のリポジトリの `git status --short` を比べる。確かめられなかった対象や観点は、試したことと一緒に控える。
4. 構成の順に書く。事実には控えた方法を添え（V2）、確かめられなかった箇所は【要確認】で残す（V4）。推奨は末尾に置く（V7）。
5. 照合する — 本文の各事実と控えた方法を突き合わせ、方法を示せない断定を除くか【要確認】に直す。
6. 納品報告に、調べた範囲、確かめられなかった対象や観点の名前、利用者のリポジトリが変わっていないことを確かめた結果を書く。

## 言語

英語と日本語の両方に対応する。英語の依頼には英語で、このファイルの原則（V1〜V8）と構成をそのまま使う。
節の名前は英語の稿では「Scope」「Results」「How to reproduce」「What could not be verified」「Recommendations」のように訳す。

style.md の S8（敬体／常体）・S9（記号）と機械スキャン（`scan.py`）は、ほかの種別と同じく日本語の稿にだけ掛け、英語の稿には掛けない。

## レビューチェックリスト（tech-review 用）

監査では、レポートが添えた URL・ファイルの行・コマンドを、たどれる範囲でたどり直す。たどれないときは、その事実を
「確認方法未確認」として報告し、事実の正否を判定しない。

- [ ] V1：冒頭に調べた範囲（対象と観点）があり、tech-write が選んだ対象なら選んだ理由があるか
- [ ] V2：各事実に確かめた方法（URL・ファイルと行・コマンドと出力）が添えられ、たどり直せるか
- [ ] V3：事実と解釈が分かれているか
- [ ] V4：確かめられなかった対象や観点が「調べられなかったこと」の節に名前つきで載り、書くはずだった箇所が【要確認】で残っているか。納品報告も渡されていれば、同じ名前が載っているか
- [ ] V5：再現方法の節に、対象の版・環境・コマンドと出力があるか
- [ ] V6：結果に計測した条件と試していない条件が添えられているか
- [ ] V7：推奨が結果と分かれて末尾の節にあり、各推奨にどの調査結果に基づくかが示されているか
- [ ] V8：調査の問い、なぜ問題か、専門用語の意味が本文で説明されているか
- [ ] style.md S8：日本語の稿の敬体／常体が規定どおりか（英語の稿には掛けない）
- [ ] style.md S9：日本語の稿の記号が規定どおりか（英語の稿には掛けない）

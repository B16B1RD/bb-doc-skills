# 手順書・チュートリアルの原則

手順書・チュートリアルの読者は「書かれたとおりに手を動かして、同じ結果にたどり着きたい」人。読者は書き手と違う環境で、
1 行ずつ実行しながら読む。1 つのコマンドが通らなければ読者はそこで止まり、後ろの手順は読まれない。
この読者に対する文書の仕事は 3 つ — (1) 自分の環境が対象かを、始める前に分からせる (2) 各手順で何が起きれば成功かを示す
(3) 止まったときに戻る道を示す。

## 対象の見分け方

読者が書かれたとおりに手を動かして進める文書を、この種別にする。インストール手順・セットアップ手順・チュートリアル・運用の手順書が当たる。

- README のインストール節は README の原則（`readme.md`）で書く。対象の環境を複数挙げるインストール手順なら、このファイルの H2・H5 も当てる（`readme.md` の R5）
- 技術トピックの概念・仕組みの解説は `topic-overview.md` で書く。読者が操作を身につけるために手を動かす文書は、この種別にする
- 画面や機能を一通り説明するマニュアル、リリースノートは未対応種別のままにする

## 原則

### H1. 対象の環境と、始める前に要るものを冒頭に書く

対象の環境（OS・シェル・道具とその入れ方）と要る権限・所要時間・終わったときに手元に何があるかを、最初の手順より前に書く。

- 検査：冒頭だけを読んで、自分の環境で始めてよいか、何を先に入れるかが分かるか。

### H2. 対象に挙げた環境ごとに、最初のコマンドが通るまでの道のりをたどる

文書が対象に挙げる環境ごとに、導入を終えた直後の読者が、文書の最初のコマンドをそのまま実行して通るようにする。
OS の違いだけでなく、同じ道具の入れ方の違い（Docker Desktop と Docker Engine のような、別の配布物）も 1 つの環境として数える。
文書が読者を外の導入の手順（公式のインストール手順など）へ送るときは、その送り先を読む。送り先が導入の後に求める手順
（権限の設定、サービスの起動、シェルの入り直しなど）は、文書に書くか、送り先の節を名指しして案内する。
送り先から足した手順には、読んだページの URL と確認した日付を、文書か納品報告に添える。

- 悪い例：Linux の読者を Docker Engine のインストール手順へ送るだけで、最初の確かめ（`docker version`）を置く。
  Docker Engine は、導入の後にユーザーを `docker` グループに入れるまで、一般ユーザーの `docker` が失敗する
- 検査：文書が読者を送る導入の手順を環境ごとに読む。送り先が導入の後に求める手順は、文書の前提・期待結果・
  つまずいたときの案内のどこかにあるか。指摘には、根拠にしたページの URL を添える。
  送り先を取得できなければ、その環境を「導入の手順を照合できなかった環境」として報告する。

### H3. 1 つの手順に、1 つの操作とその期待結果

各手順は、実行するコマンドと、成功したときに見えるもの（出力・画面・状態）を対にして書く。
コマンドはコピペで動く形にし、省略記号や、説明の無い仮の値を入れない。

- 検査：各手順に期待結果があるか。コマンドに省略記号や説明の無い仮の値が無いか。書き換えの要る箇所があれば、何に書き換えるかが直前に書かれているか。
  この項目は書き方を見る。手順が実際に通るかは H5 で見る。

### H4. 期待結果と違ったときの案内は、環境ごとの原因で分ける

期待結果と違う表示が出たときの原因と直し方を、その手順の直後に書く。原因が環境で違うときは、環境ごとに分けて書く。
1 つの環境の原因だけを書くと、ほかの環境の読者は当てはまらない直し方を試して止まる。

- 検査：つまずいたときの案内が、対象に挙げた環境の一部にしか当てはまらない原因だけになっていないか。

### H5. 手順を確かめた環境を書き、確かめていない環境を確かめたように扱わない

手順を上から通して実行した環境（確かめた日、OS、道具とそのバージョン）を文書に書く。対象に挙げたが通して実行していない環境は、
実行していないと書く。実行の記録は、利用者が渡したもの（口頭の申告を含む）か、書き手が実行したものだけを使う。記録の無い環境を推測で埋めない。
記録に日付やバージョンが無ければ、その値を【要確認】で残す。

- 検査：手順が「動く」と判定する根拠が実行の記録なら、その記録がどの環境のものかを確かめる。記録の無い環境は問題なしにせず、
  「手順を確かめた記録の無い環境」として環境名で報告する。文書に確かめた環境が書かれていなければ、H5 の指摘（重要度 medium）にする。

### H6. 後始末と次の一歩

手順で作ったもの（コンテナ、ボリューム、ファイル、サービス）の止め方・消し方と、残るものを書く。続きがあれば、次に読むものを示す。

- 検査：手順で作ったものの止め方があるか。残るデータが書かれているか。

### H7. 文体

`style.md` の検出リストを全文に適用する。手順の命令形は違反ではない（S8）。日本語文書の敬体／常体は `style.md` の S8 に、
記号は S9 に従う。

## 執筆プロセス

1. 対象の環境を決める — 利用者が挙げた環境を、道具の入れ方の違いまで分けて並べる。挙げていなければ、決まらない作業の分岐として聞く。
2. 環境ごとに、読者を送る導入の手順を読み、導入の後に求められる手順を控える（URL と確認日）（H2）。
3. 実行の記録を並べる — 利用者が渡した記録と、書き手が実行した記録を、環境ごとに分ける。記録の無い環境を控える（H5）。
4. 冒頭（H1）→ 手順（H3・H4）→ 確かめた環境（H5）→ 後始末（H6）の順に書く。
5. style.md で全文を走査する。

納品報告には、手順を確かめた記録の無い環境と、導入の手順を照合できなかった環境を名前で書く。

## 言語

英語と日本語の両方に対応する。英語の依頼には英語で、このファイルの原則（H1〜H7）をそのまま使う。
style.md の S8・S9・S11 と機械スキャン（`scan.py`）は、日本語の稿にだけ掛ける。

## レビューチェックリスト（tech-review 用）

監査では、文書のコマンドも送り先の導入の手順のコマンドも実行しない。手順が通るかは、文書・文書が読者を送る導入の手順・渡された実行の記録を読んで照らす。
H5 を「問題なしと確認した項目」に入れるのは、対象の環境のすべてに実行の記録があるときだけにする。入れるときは、記録の環境を添える。
記録の無い環境は、総評の点検の実施状況に環境名で書く。総評の本文でも、記録の無い環境の読者が最後まで進めると言い切らず、「導入の手順と照らした範囲では」のように確かめた範囲を添える。導入の手順から読み取った事実は、URL と確認日を添えて書き直し案に入れてよい。

- [ ] H1: 冒頭で、対象の環境・要るもの・所要時間・終わったときの状態が分かるか
- [ ] H2: 対象に挙げた環境ごとに、送り先の導入の手順が導入の後に求める手順が、文書のどこかにあるか
- [ ] H3: 各手順に、コピペできる形のコマンドと期待結果があるか
- [ ] H4: つまずいたときの案内が、対象の環境の一部にしか当てはまらない原因だけになっていないか
- [ ] H5: 手順を確かめた記録がどの環境のものかが分かるか。記録の無い環境が 1 つでもあれば、記録のある環境だけを挙げて H5 を問題なしにしていないか
- [ ] H6: 後始末と、残るものが書かれているか
- [ ] H7: style.md の検出リスト（S8・S9・S11 を含む）に引っかかる箇所はないか

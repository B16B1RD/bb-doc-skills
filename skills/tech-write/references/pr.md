# PR 本文／変更説明の原則

PR 本文の読者は、変更の目的と結果、影響、確認した範囲を知りたいレビュー担当者である。コード差分の正しさを評価する作業と、本文の文章を点検する作業を分ける。

## 対象の見分け方

投稿先・編集対象の明示を最優先する。「PR の説明・本文・description を書く／更新する／読みやすくする」、実際に `gh pr create`／`gh pr edit` の body／body-file に渡す文章は PR 本文として扱う。

「この PR にコメント」、レビュー指摘への返信、`gh pr comment` の本文はコメントの型を使う。Issue の起票・本文更新、`gh issue create`／`gh issue edit` の本文は Issue の型を使う。コード変更の正しさ・diff・脆弱性・テストの妥当性の評価は、コードレビューへ分ける。

対象リポジトリの PR テンプレートと複数の見出しは補助情報にする。「PR」「概要」「問題」「変更」「確認」という語や URL だけでは確定しない。CLI コマンドを文中で引用しただけでも投稿先の根拠にしない。対象が本文か diff かで作業が分岐する曖昧な依頼は、先に対象を確認する。

## 原則

### P1. 結果と目的を先に置く

冒頭の要約では、変更後に何ができるかを短く示す。各節の先頭も結論 1 文にし、必要な理由・条件を続ける。短い結論を長さの目安のために水増ししない。

### P2. 四つの役割を分ける

| 役割 | 答えること |
|---|---|
| 要約 | 変更の結果は何か |
| 問題 | どの条件で、どんな挙動に困っていたか |
| 変更 | 何が、どう変わるか |
| 確認 | 何を、どの条件で確かめたか。何は未確認か |

これは論理的な役割であり、常に四つの見出しを新設する規則ではない。既存の PR テンプレートへ対応付け、その見出し・必須欄を保つ。例えば「概要」に要約と問題、「変更内容」に変更を置き、確認はテンプレートで決められた欄へ置く。確認の欄がなければ、既存の規約に従って確認内容を補う。

### P3. 論点に応じて構造を選ぶ

一つの説明は段落、独立した変更点は別段落かラベル付き箇条書き、同じ属性で比較する変更・移動は表にする。共有文体規範の S10 に従い、一つの段落・項目・セルが独立した論点を詰めていないか確かめる。

### P4. 情報と未確認を保持する

元材料の主体・条件・数値・例外を、配置先へ対応付ける。情報を削ったり、長い表のセルや項目へ移したりするだけで短文化を完了しない。実行していない検査を検査済みとせず、未確認の範囲と理由を確認の役割に残す。

## 執筆プロセス

1. 投稿先・編集対象を確かめ、PR 本文かを判定する。
2. 既存テンプレートと元の情報を読み、四つの役割をテンプレートの欄へ対応付ける。
3. 各節の結論を先に書き、論点に応じて段落・ラベル付き項目・表を選ぶ。
4. 元情報の配置先、確認済みと未確認、S10 の論点を照合する。

## レビューチェックリスト

- [ ] P1：結果と各節の結論を先に読めるか。短い結論を水増ししていないか。
- [ ] P2：問題・変更・確認の役割を区別でき、既存テンプレートの構造を保っているか。
- [ ] P3：独立した論点を分け、同じ属性を比較できるか。項目・セルへ押し込んだだけになっていないか。
- [ ] P4：主体・条件・数値・例外が残り、確認済みと未確認を区別できるか。
- [ ] S10：長さだけで違反にせず、1 文の結論と一つの因果・条件の説明を保っているか。

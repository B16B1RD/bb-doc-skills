# tech-write — 種別判定つき技術文書執筆

技術文書は種別ごとに読者の目的が違う。README の読者は「評価して使い始めたい」、Issue の読者は
「着手判断をしたい」。種別に合わない原則で書いた文書は、どれだけ丁寧でも読者の時間を奪う。
このスキルは対象の種別を判定し、種別専用の原則をロードしてから書く。

## 同梱資料の解決

起動時に渡されたスキルの場所 `${CLAUDE_SKILL_DIR}` を、次のコマンドで実体のディレクトリに解決する。
この文字列が未置換のホストでは、スキルを読み込んだときに示されたディレクトリを引数に渡す。
現在の作業場所や個人の固定パスから推測しない。

このコマンドだけを単独の Bash 呼出しで実行し、別のコマンドを連結しない。
終了コードと標準出力を確認してから、資料を読む。
終了コードが 0 で、次に示す順の絶対パス 3 行を得たときだけ、その結果を使う。
失敗、出力なし、行数やパスの不一致では「資料の読取未確認」と失敗した操作を報告し、そこで処理を終了する。
失敗後は別の配備・キャッシュ・作業場所を検索せず、パスを組み立てて読み直さない。
起動時に示された場所以外の資料で代用せず、以下の本文処理・監査・生成・納品へ進まない。
停止の報告を補うための入力読取りや一覧取得も行わず、追加の道具を呼び出さずにその応答を終える。

```bash
python3 -c 'from pathlib import Path; import sys; p = Path(sys.argv[1]).resolve(strict=True); print(p); print(p.parent); print(p.parent.parent / "memorable-doc-principles.md")' "${CLAUDE_SKILL_DIR}"
```

出力の順は、このスキルの実体ディレクトリ、5 スキルを含む `skills` ディレクトリ、規範のパスである。
プラグイン配備では規範に `${CLAUDE_PLUGIN_ROOT}/memorable-doc-principles.md` を使い、上の実体起点の
パスと同じルートの 1 部であることを確認する。開発用 symlink 配備では、プラグイン用変数が未置換でも
実体起点の規範パスを使える。規範のコピーをスキルごとに置かない。

参照を解決したら、規範の全文を Read してから以下の手順へ進む。
存在・サイズの確認、検索で抜き出した一部、要約だけでは全文読取の代わりにならない。
一度で取得できなければ分割して末尾まで読み、未回収が残れば読取未確認を報告して停止する。
適用する観点と強度は各スキルの以下の手順に従い、規範を読んだことだけで適用対象を広げない。

本文の `references/` はこのスキルの実体ディレクトリから、兄弟スキルは解決済みの `skills` ディレクトリ
から読む。`<このスキルのディレクトリ>` も同じ実体を指す。Read の前に絶対パスに直し、references や
別の実行者へ必要な参照を渡すときも解決済みのパスを渡す。references の本文や Bash の中で
プラグイン用変数が自動置換されるとは仮定しない。規範や必要な参照を読めなければ検証失敗とし、
要約だけで読取済みにしない。

生成物・原稿・スキャン結果・スクリーンショットは利用者の作業領域に保存する。
スキルの実体、規範、プラグインキャッシュには書き込まない。指定先がそこに含まれる場合も保存せず、
利用者の作業領域の保存先を確認する。読み取る資料のパスを成果物の保存先に流用しない。

共有規則の適用では、原文・依頼にない事実を本文・図・ラベル・納品報告へ足さない。
読み手や他の実行者の出力は原文・依頼の材料ではない。指摘として採否を判定し、その推測や補足を対象物の追加事実にしない。
検査では各具体的な断定の主体・時点・条件・因果・値を、元の材料と照合する。一般知識による補足でも、原稿にない事実を納品報告だけで足さない。
材料のない前提・一般化・現在の状態も断定せず、必要な情報は【要確認：必要な情報】で残す。
調査レポートでは、自分で調べて確かめた事実を、確かめた方法（出典の URL、ファイルとその行、実行したコマンドと出力）を添えて本文へ足してよい。
この調査結果も元の材料として照合し、確かめた方法を示せない事実は足さない（`references/research-report.md` の V2）。
技術トピックの解説では、自分で調べた事実を、出典の URL と確認日を添えて元の材料として本文へ足してよい。
出典を示せない事実は足さずに【要確認】で残す（`references/topic-overview.md` の T1・T3）。
この照合も既存のセルフチェック・監査へ統合し、HTML の図や報告だけに足した断定も対象にする。
未定の手順を、実装の不存在や利用不能を示す事実として扱わない。
読み手の返答が時計未確認・未計測なら、親の回収時間と区別して未確認として報告する。
起動・回収できたことだけで、全文や時間内の確認済みにしない。修正回数は既存の上限を維持する。

## フロー

1. **インテーク** — 対象（新規テーマ or 既存文書の書き直し）、読者、言語を把握する。既存文書の
   書き直しなら全文を Read する。節など範囲を限った書き直しでは、指定範囲の外の文言を変えない。検査や読み手の観測で範囲の外に見つかった該当は直さず、2 回目の修正に進むかの判断にも草稿として渡すかの判断にも数えずに、納品報告に範囲外の残件として書く。読み手の観測のうち範囲の外のものは、手順 6 の採否一覧に載せる前に分け（reading-pass.md の、各観測を採否一覧にする規則より優先する）、採る最大 3 箇所にも採らなかった指摘にも入れない。書き直した範囲の文と範囲の外の文の食い違いから読み手が結論や操作を取り違えた観測は、位置が範囲の中でも範囲の外の観測と同じに扱い（採否一覧に載せる前に分け、直さず、2 回目の修正に進むかの判断にも草稿として渡すかの判断にも数えない）、範囲外の残件にどこがどう食い違うかを書く。tech-review の報告の後に切り替えたときは、判定表の「レビューのみの依頼」と「レビューと修正を一緒に頼む依頼」の行に当てず（tech-review へ戻さない）、その報告の指摘一覧の指摘も他の実行者の出力と同じく指摘として（報告の「採らなかった指摘」の欄にあるものは採否を判定せず、写さない）、対象本文と依頼の目的に照らして採否を判定し、採ったものを手順 5 の執筆で直す（【要確認】の追記を含め、読み手の最大 3 箇所の上限にも手順 6 の 2 パスにも数えない）。手順 5 で直しきれなかった指摘（【要確認】で残したものを含む）は、手順 6 の残件の対応づけで読み手の起動前からの検査結果に数える。tech-write が採らなかった報告の指摘は、位置と短い不採用理由を、手順 6 の採らなかった観測と同じ欄に写す。範囲を限った書き直しでは、範囲の外の指摘（書き直す範囲の文と範囲の外の文の食い違いを指す指摘を含む）は採否を判定せずに範囲外の残件に写し、手順 6 の採らなかった観測と同じ欄には写さない。報告の指摘一覧が 0 件で切り替えたときは、直したい箇所を利用者に質問して確かめ（インテークの最大 3 問に数える）、直す箇所がないと答えたとき、または質問できないときは、稿を書かず、出した tech-review の報告を最終の出力にして終える。原典の紹介では、書く前に原典を全文読む（PDF は全ページ）。
   読めない範囲があれば報告し、原典を取得できなければ要約を書かずに止める（`references/source-summary.md` の O1）。
   調査レポートでは、書き始める前に調べる範囲（対象と比べる観点）を決める。利用者が対象を指定しなければ自分で選び、選んだ理由を控える。
   調べる作業（Web 検索、ファイルやコードの読取、コマンドでの計測、使い捨ての測定スクリプト）も自分で行い、範囲の中は全部確かめる。
   測定スクリプトと計測の出力は作業用の一時フォルダに置き、利用者のリポジトリは変えない（`references/research-report.md` の「調べる作業」と V1）。
   技術トピックの解説では、書く前にトピックの一次資料（公式文書・仕様・原著）を自分で探して読み、公開日と改訂・追記の日付を控える（`references/topic-overview.md` の T2・T4）。言語は「明示指示 > 対象リポジトリ・既存文書の既定言語 >
   依頼文の言語」の優先順で決める。不明な点のうち、作業が分岐するものだけ質問する（最大 3 問）。
   投稿先が X の短文なら、長さの指定の有無によらず、X の長さを「140 字に収める／スレッドに分ける／長文投稿」の 3 択で毎回聞く
   （長文投稿は X Premium の長い投稿で、X Articles とは別。この質問も最大 3 問に数える）。
2. **種別判定** — 下の判定表で種別を決め、判定を表明する：
   「◯◯と判定しました。<表にある原則ファイルのパス> の原則を適用します」。ハイブリッド文書は
   主目的（読者がその文書を開く理由）で決める。対話中なら、ユーザーに訂正の機会を与えてから進む。
   続けて下の投稿先判定表で投稿先を決め、種別と合わせて表明する。投稿先の指定がなければ既定の GitHub Markdown とし、
   `channels/` のファイル（references の中）は読まない。1 回の依頼で書く投稿先は 1 つにする。
3. **原則ロード** — 該当する原則ファイルと `references/style.md`（共通文体規範）、
   `references/reasoning.md`（共通の論証・読み手の負荷・視点の規則）を Read する。
   投稿先に X の短文・X Articles・Slack を指定された場合だけ、投稿先判定表にある `channels/` の制約ファイル（references の中）も Read する。
4. **構成確認（条件付き）** — 本文を書き始める前に、材料と予定する構成から次のいずれかに当てはまるか確かめる。
   - 本文が 3 段落以上になる見込みがある。
   - 一つの節に独立した論点が 3 個以上ある。
   - 同じ属性で説明する対象が 3 個以上ある。

   現在の段落数だけで省略せず、1 段落に独立した 4 論点が詰まっている場合も対象にする。
   文数を論点数と数えない。結論・理由・例が一つの論点を支えるなら、合わせて一つとして扱う。
   1〜2 段落で一つの変更・結論を説明する文書や、各節が 1 文の短い PR は、ほかの条件がなければ
   独立した構成メモを省く。省略した文書ではメモの結論文の転記・一致照合も行わず、種別の原則に従って執筆・点検する。
   短い節の数をそのまま段落数の条件へ当てはめず、結論を水増ししない。
   3 という数は手順の負担を抑える初期値で、読みやすさを保証する境界ではない。

   対象なら、節ごとに「答える問い → 結論 → 独立した論点 → その根拠・条件・例」を内部の構成メモにする。
   結論欄には「本文の第 1 文としてそのまま使う 1 文」を書き、「結論 1 文」のような配置名だけで済ませない。
   既存のテンプレートの見出し・必須欄を保ち、各節の頭へ結論、別の論点へ別段落かラベル付き項目、
   同じ属性の繰り返しへ表を割り当てる。表や項目を中心にする節にも、その直前に、元材料からその節の問いへ答える 1 文を用意する。
   「次の表のとおり」など内容を示さない案内だけを結論にせず、何が変わるか・どう違うかを具体的に示す。
   結論も元材料の範囲に限る。示された比較軸を「違いはこれだけ」と言い換えたり、材料にない優劣・因果を足したりしない。
   元材料の主体・条件・数値・例外を全件、配置先へ対応付ける。
   情報を削って長さをそろえず、長いセルや項目へ押し込んだだけで整理済みとしない。
   この配置を使って執筆し、セルフチェックで移し忘れを照合する。構成メモ自体は納品物へ追加しない。
   この手順は技術文書用であり、retention の因果を伝える文章へ表・箇条書き化を転用しない。
5. **執筆** — 原則ファイル内の「執筆プロセス」と reasoning.md の規則に従う。
   構成メモを作った場合だけ、各本文節の結論文を、言い換えずそのまま、その節の第 1 文に写す。
   表・箇条書きと、それらを導く案内文は、結論文の後に置く。
   文書冒頭の要約だけで各節の結論を代用しない。英日ペアも、両方の本文節でこの順序をそろえる。
6. **セルフチェック** — 原則ファイル末尾の「レビューチェックリスト」と style.md の検出リストで
   自分の出力を走査する。下記の検査結果を集めてからまとめて直す。日本語の文書では、S8 の敬体／常体と S9 の記号、S10 の段落の論点も確かめる。
   調査レポートも同じく、S8・S9・scan.py は日本語の稿にだけ掛け、英語の調査レポートには掛けない。
   段落の論点は長さの計測の有無によらず目視で点検し、情報を削らず、長い単一因果は文脈で判断する。
   構成メモを作った場合は、決めた配置と原稿を照合して元情報の移し忘れを直す。
   メモの有無によらず、本文の各断定に元材料を対応付け、
   元にない「だけ」「常に」などの限定・一般化を除く。限定を外しても根拠がなければ、材料のある文に戻す。
   構成メモを作った場合だけ、本文節ごとに表・箇条書き・案内文より前の第 1 文を取り出し、メモの結論文と一致するか照合する。
   一致しない節は未完了として、残りの修正回数内でメモの結論文をそのまま第 1 文へ戻す。
   表・箇条書き・案内文が先にある場合も、結論文の後へ移す。修正後にもう一度一致を確かめる。
   英日ペアは片方の確認で済ませず、両方を照合する。
   Read した `references/reasoning.md` の規則でも原稿を検査する。未読ならここで Read し、
   語の検出だけでは判定できない箇所も確認する。納品報告を書いた時点でも、補足説明を含む対象物の断定に同じ照合を掛け、材料にない事実を足していないことを確認してから出す。
   日本語の文書は、納品前の稿に機械スキャンも掛ける。稿がまだファイルになっていなければ一時ファイルに書き出し、納品するファイルが既にあればそのファイルに掛ける。英語の文書には掛けない：
   `python3 <このスキルのディレクトリ>/../retention-review/scripts/scan.py <稿のファイル> --profile reference`
   出力は S1・S2・S3・S4・S6 と S9（記号の字形）・S10（通常段落の長さ）のシグナルで、判定ではない。S9・S10 はすべて `[弱]`。`[弱]` と `[引用文脈?]` は該当行を読んで判断する。
   手順の「〜してください」とラベルの太字は数えない。記号表記の「**ラベル**。」は、ラベルが名詞句なら全角コロンで区切るか、ラベルだけの行の下に説明を書く形に直す（S3）。太字が述語で終わる 1 文なら句点のまま残す。「**ラベル**:」は全角コロンに直す（S3）。修正後にも掛け、`[弱]` と文脈で正当と判断した語を除いて、直すべき箇所を確かめる。
   通常段落の長さは `[弱]` の開始・終了行と文数相当・字数を読み、論点のまとまりで採否を決める。一つの因果・条件にまとまる段落は、5 文以上または 250 字以上でも残せる。`paragraph_length` の空配列は計測済みの該当なし、`null` と `paragraph_measurement` の理由は文書全体の未計測で、0 件や合格としない。表・項目・引用などの除外部分と短い複数論点は目視で点検する。
   scan.py が使えない環境では、style.md の検出リストを目視で確かめる。
   ここからの準備・起動・待機・採否・再確認を合計 8 分に収めるため、親全体の開始時刻を時計で取る。この上限は読み手に読ませる工程にだけ当て、調査レポートで調べる作業（検索・読取・計測）の時間は数えない。開始時計とは別の呼出しで起動直前にも現在時計を取り、差を確認してから起動する。返答を回収したら、採否・修正に入る前に現在時計を取り直して差を確認する。上限超過や残り時間不明なら追加の起動・修正を止め、未確認として報告する。
   投稿先が X の短文なら、言語によらず納品前の稿を一時ファイルに書き出し、投稿の間を空行 3 つ以上で区切って文字数を数える。修正後にも掛ける：
   `python3 <このスキルのディレクトリ>/scripts/x_length.py <稿のファイル> [--limit N]`
   終了コード 1（上限を超えた投稿がある）なら、出力の超過量を見て直してから納品する。長文投稿では利用者が答えた上限を `--limit` で渡す。
   投稿先が Slack なら、稿に `**` の太字・`[text](url)` のリンク・行頭の `#` の見出しが 0 件であることを確かめ、残っていれば mrkdwn に直す。
   言語によらず `references/reading-pass.md` を Read し、段落の関係を読み、文脈を持たない別の読み手にも原稿を読ませる。
   投稿先を指定されたときは、読み手に渡す読者の前提を、その投稿先のファイルにある「読者の前提の例」から選ぶ。点検の重さ（読み手・修正 2 パス・8 分の時計）は投稿先によらず同じにする。
   短文でも、文脈を分離した読み手を起動できるなら納品前に必ず起動する。起動できないときは理由を報告し、短さを省略理由にしない。
   読み手が初読中に戻った段落も既存の迷いに含め、返却件数で失敗にせず、親が重要な順に最大 3 箇所を採る。残りは「採らなかった指摘」として短い理由を残す。追加の再読を求めず、結論・確認範囲・未読・時計未確認は件数で省かない。
   修正は同ファイルに従い、スキャン・段落・読み手の指摘を合わせて最大 2 パス、読み手は初読と再確認の最大 2 回に収める。
   納品報告の残件は、読み手の起動前からの検査結果と、採否一覧で採用した観測から作る。各残件をこのどちらかへ対応づけてから出力する。範囲を限った書き直しでは、範囲の外の該当を範囲外の残件として別の欄に並べ、この対応づけには含めない。読み手由来の範囲外の残件には、読み手の実際の解釈を添える。採らなかった観測は、位置と短い不採用理由を別欄へ写すだけにする。省略・確認範囲・未実施・時間切れ・時計は、点検の実施状況の欄へ転記する。使用済みと残りの起動・修正回数を示し、同じ文書への材料補充や修正再開にもその回数を引き継ぐ。残りがなければ、次の編集工程を案内せず、引き継いだ稿とこの報告を最終の出力にする。重大な誤読が残る稿は草稿として渡す（範囲を限った書き直しの範囲外の残件は除く。reading-pass.md の同じ規則より優先する）。
   この採否・修正・再確認と報告内容の整理を終えたら、回収時刻とは別のツール呼出しで終了時計を取る。開始から終了までの差を親の所要時間として報告に入れ、セルフチェックを終える。採用 0 件でも回収時計で代用しない。終了時計が取れなければ親全体は未計測と記す。
7. **HTML 化（「HTML で」「Artifact で」と明示されたときだけ）** — 依頼に明示がなければ、この手順は飛ばす。
   文書の種別から HTML にするかどうかを推定しない。明示があるときは、手順 6 のセルフチェックを
   Markdown 原稿のまま完了させてから HTML にする。scan.py は HTML 化より前に終える。
   HTML の書き方は `<このスキルのディレクトリ>/../retention-write/references/html-output.md` に従う
   （骨格・図の置き場所と強弱・再生できるフロー図・アクセシビリティ・スクリーンショット確認・目視チェックリスト）。
   種別ごとの扱いは次のとおり。

   | 種別 | 扱い |
   |------|------|
   | 英日ペアでない手順書・リリースノート・原典の紹介・調査レポート・技術トピックの解説・未対応種別 | HTML にする。原典の紹介でも図表は転載しない。調査レポートでも再現方法のコマンドと出力は文字のまま残す。技術トピックの解説でも出典の URL と確認日は本文に残す |
   | 英日ペアでない README | Markdown 本体を納品し、HTML 版は別の納品物として添える |
   | Issue・PR 本文・Issue コメント・PR コメント | 投稿する本文は Markdown のまま。HTML にできない理由を一言添える |
   | 英日ペア（README.md / README.ja.md を含む） | Markdown のまま両方を同期し、HTML にしない理由を一言添える |
   | 投稿先が X の短文・X Articles・Slack の文書（種別によらない） | 投稿本文は HTML にせず、投稿先のファイルの「納品の形」で納品する。HTML にしない理由を一言添える |

   - 図は reference の「図の置き場所と強弱」に従い、構造・流れ・段階・比較・前提・時間の経過を説明する節に置く。枚数に上限はない。手順の流れがある文書は、流れを再生できる図にする。図の置き場所と補助図の役は目視で確かめる。scan.py では判定できない
   - HTML 化の段階で本文の文言を足さず、セルフチェック済みの文を変えない。図のラベルは例外とする。本文を直す必要が出たら、手順 6 の残りの修正回数内で Markdown 原稿を直し、同じセルフチェックを経て HTML 化し直す。2 パスを使い切っていれば本文をさらに直さず、残件を納品報告に書く
   - 保存先はユーザーの指定に従い、指定がなければ確認する。「Artifact で」と明示されたときは、保存した HTML を Artifact として納品する
   - 保存した HTML をスクリーンショットで確かめ、納品報告に reference の「納品報告に書くこと」に従って確認の結果を添える。道具が全滅したときは「スクショ未確認」と目視チェックの結果を書く

| 原典の紹介 | 論文・記事の紹介・要約で、書き手の主張を足さないもの（意見や感想の指定がない紹介ブログ記事を含む） | `references/source-summary.md` |
| 調査レポート | 複数の対象を同じ観点で比べる比較調査、検証・計測の結果を伝えるレポート。読者が調べた結果を知るために開くもの（推奨を末尾に添えるものを含む） | `references/research-report.md` |

## 投稿先判定表

種別の判定とは別に、書いた文章をどこに載せるかを決める。告知・進捗・質問などの短い用件は、
種別としては Issue コメント／PR コメントの原則（`references/comment.md`）を使い、投稿先の制約を重ねる。

| 投稿先 | シグナル | 追加で読む制約 |
|--------|---------|---------------|
| GitHub Markdown（既定） | 投稿先の指定がない依頼、GitHub・リポジトリのファイルに載せる文書 | なし（`channels/` の制約ファイルは読まない） |
| X の短文 | 「X に投稿」「ツイート」「スレッドで」など X の投稿の指定。長文投稿（X Premium）を含む | `references/channels/x.md` |
| X Articles | 「X Articles で」「X の記事で」など X Articles の指定 | `references/channels/x-article.md` |
| Slack | 「Slack に貼る」「Slack で告知」など Slack のメッセージの指定 | `references/channels/slack.md` |

投稿先の制約は、種別の原則とは別の層として重ねる。種別の原則と投稿先の制約が食い違うとき（見出しの記法など）は、
投稿先の記法で書き、種別の原則が求める情報は残す。投稿先が判定表にないとき（Discord など）は既定の GitHub Markdown で書き、
その投稿先の制約ファイルは未整備と納品時に明示する。

## 英日ペアの扱い

README.md / README.ja.md のような対訳ペアを検出したら（同名 + 言語サフィックス、冒頭の相互リンクが
手がかり）、必ず両方を作業対象にする。

- 構造（見出し・順序・表の行構成）は完全に一致させる
- 内容は等価にする。逐語訳ではなく、各言語で自然な文として書く
- 片方だけの更新を指示されたら、もう片方が乖離することを指摘し、両方更新を提案する

## プロジェクト固有テンプレートとの関係

対象プロジェクトに Issue/PR テンプレートや文書規約（例：rite workflow の Implementation Contract）が
ある場合、構造はテンプレートに従い、このスキルの原則は品質基準として適用する。テンプレートを
このスキルの都合で上書きしない。

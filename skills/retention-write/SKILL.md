# retention-write — 記憶に残る文書を書く

このスキルの中核は文章術ではなくプロセス規則である：本文より先に「賭け金」と「想起 3 問」を決める。本文から書き始めた文書は、原則を後から塗っても空洞が残る——3 問に答えられない文書は、まだ書く準備ができていない。

規範：「記憶に残る文書設計の原則」（v0.1）。以下で解決した規範の全文を執筆前に Read する。

## 同梱資料の解決

起動時に渡されたスキルの場所 `${CLAUDE_SKILL_DIR}` を、次のコマンドで実体のディレクトリに解決する。
この文字列が未置換のホストでは、スキルを読み込んだときに示されたディレクトリを引数に渡す。
現在の作業場所や個人の固定パスから推測しない。

このコマンドだけを単独の Bash 呼出しで実行し、別のコマンドを連結しない。
終了コードと標準出力を確認してから、資料を読む。
終了コードが 0 で、次に示す順の絶対パス 3 行を得たときだけ、その結果を使う。
失敗、出力なし、行数やパスの不一致では「資料の読取未確認」と失敗した操作を報告し、そこで処理を終了する。
失敗後は別の配備・キャッシュ・作業場所を検索せず、パスを組み立てて読み直さない。
起動時に示された場所以外の資料で代用せず、以下の本文処理・監査・生成・納品へ進まない。
停止の報告を補うための入力読取りや一覧取得も行わず、追加の道具を呼び出さずにその応答を終える。

```bash
python3 -c 'from pathlib import Path; import sys; p = Path(sys.argv[1]).resolve(strict=True); print(p); print(p.parent); print(p.parent.parent / "memorable-doc-principles.md")' "${CLAUDE_SKILL_DIR}"
```

出力の順は、このスキルの実体ディレクトリ、5 スキルを含む `skills` ディレクトリ、規範のパスである。
プラグイン配備では規範に `${CLAUDE_PLUGIN_ROOT}/memorable-doc-principles.md` を使い、上の実体起点の
パスと同じルートの 1 部であることを確認する。開発用 symlink 配備では、プラグイン用変数が未置換でも
実体起点の規範パスを使える。規範のコピーをスキルごとに置かない。

参照を解決したら、規範の全文を Read してから以下の手順へ進む。
存在・サイズの確認、検索で抜き出した一部、要約だけでは全文読取の代わりにならない。
一度で取得できなければ分割して末尾まで読み、未回収が残れば読取未確認を報告して停止する。
適用する観点と強度は各スキルの以下の手順に従い、規範を読んだことだけで適用対象を広げない。

本文の `references/` はこのスキルの実体ディレクトリから、兄弟スキルは解決済みの `skills` ディレクトリ
から読む。`<このスキルのディレクトリ>` も同じ実体を指す。Read の前に絶対パスに直し、references や
別の実行者へ必要な参照を渡すときも解決済みのパスを渡す。references の本文や Bash の中で
プラグイン用変数が自動置換されるとは仮定しない。規範や必要な参照を読めなければ検証失敗とし、
要約だけで読取済みにしない。

生成物・原稿・スキャン結果・スクリーンショットは利用者の作業領域に保存する。
スキルの実体、規範、プラグインキャッシュには書き込まない。指定先がそこに含まれる場合も保存せず、
利用者の作業領域の保存先を確認する。読み取る資料のパスを成果物の保存先に流用しない。

共有規則の適用では、原文・依頼にない事実を本文・図・ラベル・納品報告へ足さない。
検査では各具体的な断定の主体・時点・条件・因果・値を、元の材料と照合する。
材料のない前提・一般化・現在の状態も断定せず、必要な情報は【要確認：必要な情報】で残す。
この照合も既存のセルフチェック・監査へ統合し、HTML の図や報告だけに足した断定も対象にする。
未定の手順を、実装の不存在や利用不能を示す事実として扱わない。
読み手の返答が時計未確認・未計測なら、親の回収時間と区別して未確認として報告する。
起動・回収できたことだけで、全文や時間内の確認済みにしない。修正回数は既存の上限を維持する。

## 進め方

### 0. 適用判断

- 参照文書（API リファレンス・手順書・一覧表）は対象外。普通に書いてよい。
- 短い連絡・周知メモは軽量モード（skeleton.md の連絡メモテンプレ。原則 1・3・6 のみ、クイズ・比喩は付けない）。
- 判断を伝える文書（設計メモ・ADR・提案・障害報告・主張のある記事）はフルプロセス（1〜4）。

### 1. インテーク（1 回・最大 4 問）

聞くのは、ユーザーの頭の中にしかないことだけ。会話・添付ファイル・コードベースから分かることを聞き直すのは面倒の押し付けであり、インテークが面倒になった瞬間このプロセスは使われなくなる。質問は 1 回にまとめ、4 問を上限とする。優先順：

1. 決定・主張は何か（期限・責任者があるなら合わせて）——賭け金の材料
2. 読者は誰で、1 週間後に何を覚えていてほしいか——想起 3 問の材料。読者との関係（上位・同格・部下・社外）は文体レジスタの入力にもなる
3. 起点となった出来事と実測値（いつ・何が・どの数字）——因果の物語と具体の材料
4. 検討して捨てた案とその理由——却下案の材料

対話できる環境では AskUserQuestion で 1 回にまとめて聞く。「わからない」「まだ決めてない」も有効な回答で、埋めさせようと粘らない。

対話できない環境（ヘッドレス・サブエージェント実行）では質問せず、会話にある情報だけで書く。無い事実は創作しない。数値・日付・固有名のでっち上げは、このスキルの目的を毒に変える——偽の具体は偽のまま読者に記憶される。不足箇所は初稿の本文中に【要確認: 必要な情報】を置く。納品時の一覧は手順 5 で作る。

### 2. 書く前に書く

本文の前に、次の 2 つを作って提示する：

- 想起 3 問のドラフト（型は skeleton.md: メカニズム・却下理由・再検討条件）
- 賭け金の一文（立場・期限・責任者・理由）

短い文書ではそのまま同じターンで本文まで書き進めてよい。長い文書（提案書・記事・重要な ADR）ではここで一度止めて確認を待つ——3 問を直すのは本文を直すより 10 倍安い。

### 3. 執筆

`<このスキルのディレクトリ>/../tech-write/references/reasoning.md` を Read し、共通規則と
同ファイルの「原則との優先順位」に従う。

`references/skeleton.md` のスケルトンに沿って書く。要点：

- 文体の既定は敬体（です・ます調）。上書きするのは、指示文の明示キーワード（「である調で」「常体で」）と、既存文書への追記でその文書の文体を継ぐ場合の 2 つだけ。文書の種別から既定を推定しない
- 記号（括弧・コロン・範囲・三点リーダーなど）の字形と用途は `<このスキルのディレクトリ>/../tech-write/references/style.md` の S9 を Read して従う。
- 同じ style.md の S10 を Read し、1 段落 1 独立論点と長さの弱い目安に従う。因果の物語は出来事・原因・結果の意味の切れ目で分け、因果を示す文と主体・条件・数値・例外を残す。長さだけを理由に表や箇条書きへ変えない。
- どちらの文体でも語り口は中立に保つ。断定は決定と理由の明示で行い、「〜しましょう。」「〜してください。」の指示・勧誘、「〜からだ。」「〜それだけだ。」の詠嘆、「〜してほしい。」の読者指示は使わない（規定の本体は `references/skeleton.md` の文体レジスタ節にある 2 軸表と上書き規則。部下への指示文書・私的な文章だけが例外）
- 第一段落 = 賭け金。前置き・挨拶・「本ドキュメントでは」で始めない
- 中核は因果の物語（いつ・誰が・何を・なぜ・どうなった）。数字は丸めない
- 比喩は中核主張と構造同型のものを 1 本だけ、主役級で使う
- 山場（意外な数字・反直観な結論）の直前に生成の問いを 1 つ
- 捨てた案は理由一文 + 「却下。」。留保は末尾に一度だけ
- 強調（太字）は「1 週間後に残す一文」の 1 箇所のみ
- 末尾に読了チェック 3 問（手順 2 のドラフトを本文に合わせて磨いたもの）
- 新しい漢語の名前を当てる前に、既存の一般語か素直な文で言えないかを試す。言えるならそちらを使う。英語概念に訳語を自作しない

### 4. セルフチェック（納品前）

Read した `<このスキルのディレクトリ>/../tech-write/references/reasoning.md` の規則でも原稿を検査する。
未読ならここで Read する。機械スキャンの判定と共通規則の関係は、同ファイルの「原則との優先順位」に従う。

S10 の段落の論点も目視で点検する。長さの目安を超えても一つの因果・条件にまとまるなら残せる。短い複数論点は分け、1 文の結論を水増ししない。情報を削ったり項目・セルへ移したりしただけでは解消にしない。

原稿を一時ファイルに置き、retention-review の機械スキャンを掛ける：

```bash
python3 <このスキルのディレクトリ>/../retention-review/scripts/scan.py <原稿ファイル>
```

通常段落の長さは `[弱]` の開始・終了行と文数相当・字数を読み、論点のまとまりで採否を決める。一つの因果・条件にまとまる段落は、5 文以上または 250 字以上でも残せる。`paragraph_length` の空配列は計測済みの該当なし、`null` と `paragraph_measurement` の理由は文書全体の未計測で、0 件や合格としない。表・項目・引用などの除外部分と短い複数論点は目視で点検する。

基準（強シグナル・弱シグナルの二段。弱シグナルは scan.py 出力の `[弱]` 表示で見分ける）：

- **強シグナルは 0**：フィラー 0 ／ 死んだ比喩 0 ／ 万能語 0 ／ 文体レジスタ 0 ／ ヘッジは留保の 1 回だけ（いずれも引用内を除く）。1 件でも残っていたら直す。ただし修正は下の収束ループで最大 2 回までで、残った分の扱いもそこに従う。文体レジスタ（`principle_6_style_register`）は敬体・常体のどちらで書いていても詠嘆・指示の語形だけを拾うので、上書きで常体を選んだ原稿でも基準は同じ 0 である
- **弱シグナルは文脈判断**：解決済みの `skills` ディレクトリから `retention-review/references/scan-guidance.md` を Read する。正当な万能語と事実的不確実性を、空疎な主張と区別する。機械的に 0 にせず、具体語で置換できるときは置換する。原因と条件が特定された外部事象の不確実性は残し、書き手の主張をぼかしているだけなら直す
- **記号表記は弱シグナル**：日本語の本文にある半角の括弧・コロン・スラッシュ、`~` と「～」、単体の「…」、半角の二重引用符、句点で区切った箇条書きのラベル（`**ラベル**。`）、日本語を含む行でラベルを半角コロンで区切った箇条書きのラベル（`**ラベル**:`）が、`[弱]` つきの「記号表記」として出る。`tech-write/references/style.md` の S9 の字形（（ ）・「：」・「／」・「〜」・「……」・“ ”）に直す。`**ラベル**。` は、ラベルが名詞句なら全角コロンで区切るか、ラベルだけの行の下に説明を書く形に直し（S3）、太字が述語で終わる 1 文なら句点のまま残す。`**ラベル**:` は全角コロンに直す（S3）。引用された悪例や、コード・表・URL に近い用法なら残してよい。基準の強シグナルには数えないので、「強シグナルは 0」と収束ループの回数は変わらない
- 強調 1 箇所以下 ／ 判断文書なら生成の問いと想起テストが「有」（従来どおり）

段落長の baseline 比較は別欄の対象数・該当件数・最大値で、段落の移動の同一性は追わない。旧 baseline の段落情報なしや未計測は比較不能と報告し、語句の resolved と混ぜない。

**解消と数える条件**：万能語とヘッジが解消したと数えるのは、具体的な値・固有名に置き換えたときか、その語を含む文ごと削ったときだけである。辞書にない同義語への言い換え（「最適化」を「改善」にするなど）は、再スキャンの resolved にその語が出ても解消と数えない。resolved に出た語を自分の修正内容と突き合わせて、言い換えで済ませた語を特定する。件数を下げるためだけに、新しい短い断定文を差し込まない。

**未解消**は、基準を超えて残っている強シグナルと、解消と数えない言い換えをまとめた呼び名である。強シグナルは上の基準の 5 種（フィラー・死んだ比喩・万能語・文体レジスタ・ヘッジ）のうち `[弱]` 表示でないものをいい、基準が許す分（留保の 1 回、引用内、部下への指示文書・私的な文章での文体レジスタ）、弱シグナル、強調・想起テストの印は数えない。`--baseline` の new と resolved の行には `[弱]` が付かないので、その語を上段の明細と突き合わせて見分ける。収束ループの終了と手順 5 の報告は、この未解消で決める。scan.py の件数が 0 でも、言い換えで済ませた語があれば未解消である。

scan.py が使えない環境では skeleton.md 末尾の対照表で目視チェックする。目視には new も resolved もないので、1 回目の修正の後の見直しで未解消が残っていなければ 2 回目に進まない。修正は最大 2 回まで、解消と数える条件と残った分の報告は同じである。

ここからの準備・起動・待機・採否・再確認を合計 5 分に収めるため、親全体の開始時刻を時計で取る。開始時計とは別の呼出しで起動直前にも現在時計を取り、差を確認してから起動する。返答を回収した直後の最初の操作は、現在時計の取得と開始からの差の確認にする。その後で採否・修正へ進む。「指摘なし」「採用なし」「軽い判断」と決めることも採否に含み、軽量モードでもこの時計を省かない。採否・修正・再確認を終えた後にも終了時計を取り、親全体の所要時間を求める。回収直後の時計を終了時計に代用しない。上限超過や残り時間不明なら追加の起動・修正を止め、未確認として報告する。
`<このスキルのディレクトリ>/../tech-write/references/reading-pass.md` を Read し、段落の関係を読み、文脈を持たない別の読み手にも原稿を読ませる。
短文や軽量モードでも、文脈を分離した読み手を起動できるなら納品前に必ず起動する。起動できないときは理由を報告し、短さを省略理由にしない。
読み手が初読中に戻った段落も既存の迷いに含め、返却件数で失敗にせず、親が重要な順に最大 3 箇所を採る。残りは「採らなかった指摘」として短い理由を残す。追加の再読を求めず、結論・確認範囲・未読・時計未確認は件数で省かない。
スキャンと段落の点検で修正対象と判断した項目に、reading-pass.md で採用した読み手の観測を重複統合し、修正対象の一覧を作る。この一覧をまとめて修正する。以下の最大 2 回は、3 つを合わせた修正パスの回数である。
読み手は初読と初回修正後の再確認の最大 2 回までとし、時間・文脈の分離・未実施の扱いも同ファイルに従う。

違反が残っていた場合、修正は 1 パスで終えず `--baseline` の収束ループで行う。修正は最大 2 回までで、再スキャンの未解消・段落の関係・読み手の採用した指摘がすべて 0 件になれば、残りの修正に進まない。未実施・未確認は 0 件と扱わず報告する：

```bash
# 1. 初回スキャン結果を JSON で保存する
python3 <このスキルのディレクトリ>/../retention-review/scripts/scan.py <原稿ファイル> --json > /tmp/scan-prev.json
# 2. 原稿を修正する
# 3. 前回結果を baseline に再スキャンし、resolved / new / persisting を確認する
python3 <このスキルのディレクトリ>/../retention-review/scripts/scan.py <原稿ファイル> --baseline /tmp/scan-prev.json
```

「修正 → 前回の JSON を `--baseline` に再スキャン → 今回の結果を `--json` で保存し直す」と段落の関係の再確認を、採用した指摘がなくなるまで繰り返す。読み手の再確認は初回修正後の 1 回だけで、2 回目の修正後は起動しない。読取の時間切れは reading-pass.md に従い、未確認の稿を問題なしと扱わない。ただし修正は 2 回までで、3 回目の修正はしない。resolved が自分の意図した修正と一致していること（直したつもりの違反が resolved に現れていること）も確認する。修正が新たな違反を生んでいれば new に現れるので、1 回目の後ならそこで手を止めて直す。スキャンが収束しても段落の関係や読み手の採用した指摘が残れば、残りのパスで直す。2 回目の修正後は、一覧のうち未解消の項目を手順 5 の残件として渡す。採らなかった観測の位置と短い理由、検査の実施状況は、それぞれ別に渡す。

自分の文章にレビューを掛けてから出す——このスキルと retention-review は同じ規範の生成側と監査側である。

### 4.5 HTML 化（「HTML で」「Artifact で」と明示されたときだけ）

依頼に「HTML で」「Artifact で」の明示がなければ、この手順は飛ばして手順 5 へ進む。文書の種類から HTML にするかどうかを推定しない。

明示があるときは、手順 4 を Markdown 原稿のまま完了させてから HTML にする。scan.py のセルフチェックは HTML 化より前に終える。HTML の書き方は `<このスキルのディレクトリ>/../retention-write/references/html-output.md` に従う（骨格・主役図と補助図・再生できるフロー図・アクセシビリティ・スクリーンショット確認・目視チェックリスト）。

- 主役図は、中核の比喩（手順 3 の比喩）を描いた 1 枚にする。太字の強調は手順 3 と同じく 1 箇所のままにする
- 読了チェック 3 問を HTML にも載せる。`<details>` で答えを開く形にするかは、ユーザーの指定があればそれに従い、なければ常時表示にする
- 因果の物語にフローがあるときは、再生できる図にする
- 補助図は、reference の 3 基準（担う役を一文で言える・主役図と張り合わない・消して失うものがなければ削る）を目視で確かめる。scan.py では判定できない
- HTML 化の段階で本文の文言を足さず、セルフチェック済みの文を変えない。図のラベルは例外とする。本文を直す必要が出たら、Markdown 原稿を直して scan.py と段落の関係を再確認してから HTML 化し直す。読み手の再確認も残りの回数内で行い、時間切れと未確認稿の報告は reading-pass.md に従う。掛け直しは手順 4 の収束ループで行い、違反を直す修正は手順 4 の「2 回まで」に数える
- 軽量モード（連絡メモ）で HTML を求められたときは、図を付けず、骨格だけ HTML にする
- 保存した HTML をスクリーンショットで確かめる。道具が全滅したときは、目視チェックリストでソースを確認し、納品報告に「スクショ未確認」と目視チェックの結果を書く

### 5. 納品

納品報告で本文を要約するときも、数値が掛かる対象・期間・条件を原稿と照合する。一工程の所要時間を復旧全体へ広げたり、本文に残した不明な範囲を報告だけで断定したりしない。

本文と読了チェック 3 問（判断文書の場合）を示す。納品報告には、手順 4 から渡された残件、採らなかった指摘の位置と短い理由、検査の実施状況、使用済みと残りの起動・修正回数、残り回数で可能な次の工程を順に載せる。次の工程がなければ、引き継いだ草稿をそのまま示し、本文へ【要確認】などを追記せず残件の報告で終える。材料補充後も同じ文書の使用済み回数を引き継ぐ。
残件の引用・位置・理由を転記し、読み手由来の項目には実際の解釈を添える。スキャンの未解消は行番号と語を示す。末尾の【要確認】一覧は、納品する原稿と、この残件欄にある【要確認】を重複なく転記して作る。省略・確認範囲・読み手の未実施や時間切れ・未確認稿を reading-pass.md に従って報告する。重大な誤読が残るときは完成扱いにせず草稿として渡す。保存先はユーザーの指定に従い、指定がなければ提示だけして保存先を確認する。

手順 4.5 を通した場合は、納品物を HTML ファイルまたは Artifact にする。納品報告には、reference の「納品報告に書くこと」に従ってスクリーンショット確認の結果（どの道具でどの幅か、「スクショ未確認」「ダーク未確認」、直せなかった崩れ、道具が全滅したときの目視チェックの結果）を添える。

## してはいけないこと

- インテークを 2 往復以上にしない。4 問で足りない企画は、このスキルではなく unknowns（探索）の仕事
- 事実の創作。実測値がなければ【要確認】のまま出す方が、もっともらしい偽数字より価値が高い
- 連絡メモへの過剰適用（クイズ・比喩・物語化）。軽量モードの範囲を守る
- 明示のない HTML 出力。「HTML で」「Artifact で」の指示がない依頼は、文書の種類にかかわらず Markdown で納品する
- 仕上げの文体調整（「AI っぽい表現」の引き算）を理由に構成原則を崩さない。引き算は最後、構成が先
